## 关键决策

### 1. 采方案 B：自写两级 CacheManager

Spring 的 `@Cacheable` **不原生支持两级**（一个 `CacheManager` 就是一层）。三案取舍：

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 只做 Redis 单级 | 注解干净 | 每次跨网络 |
| **B. 自写两级 CacheManager** | **本地命中不打网络** | 100–200 行基础设施 |
| C. 业务层手写两级 | 灵活 | 注解优势丢失、代码散落 |

选 B 的理由是**一次性封装、后续改造不碰业务代码**：C 的成本随改造次数线性增长。
方案 B 与「Service 抽取」是同一件事的两半 —— Service 提供**注解落点**，两级 CacheManager 提供
**注解背后的实现**。

### 2. §0 硬约束：缓存不得落在「先查后插」的查重查询上

这是整个 B1 的**第一优先级约束**，也是「为什么必须抽 Service」的真正原因。原 `goodstype`
一个方法里同时装着 GET 读分支与 POST 写分支，`@Cacheable` 挂上去会**连写分支一起缓存**，
而写分支里的 `SELECT COUNT(*)` 查重正是 **B-2 的 TOCTOU 缺陷**之一 —— 一旦被缓存，
A3 最值钱的那条证据就**假绿**了。

**故 §0 的判据不是「哪个接口读多」，而是「这个方法体里有没有查重 SELECT」。** 三处 TOCTOU
（`goodstype` / `goodsAdd` / `friendAdd`）**一行未碰**，回归里 5/5 复现即是证据。

### 3. cacheName 不能随便合并 —— 两种代价，第二种会静默出错

`goods` 族分裂成 4 个 cacheName、`friend` 族 2 个，都**有意不合并**，但理由**不同**：

- **goods 族**：两个投影值形状不同（`{price, goodImg}` vs `List<String>`）⇒ 合并后
  `Cache#get(key, type)` 会抛 `IllegalStateException` —— **响亮**的失败。
- **friend 族**：两个投影值形状**完全相同**（都是 `List<Map>`）⇒ 同一个键串先缓存「222 的好友」
  再读「222 的申请」，会把好友列表**当作申请列表返回** —— **不抛异常、静默串味**。
  第二个理由：键列不同（`customerid` vs `friendid`）⇒ 同一字符串在两族里语义不同。

**判据沉淀成一句**：值形状**可辨**（不同类）合并只会响亮失败，尚可救；值形状**不可辨**时合并是静默错答。
后者才是真危险。

### 4. 写路径 evict：单入口 + 「唯一出口前**无条件**」

D 笔把 12 行注解收敛成 `GoodsCacheService.evictByMerchant()` 一处。代价与收益：

- **收益**：写接口不必记得「我这张表有几个 cacheName」；三个调用点同名同形、可 grep 计数。
- **代价**：语义从「注解自动清」变成「**显式调用清**」⇒ **漏写那一行是静默的**（不报错、陈旧到 TTL 自愈）。

**placement 判据扩成两个方向**（本笔新增第二个）：

1. `userSelect` 那笔靠「`loginAdd` 是 `@Transactional`、异常路径回滚 ⇒ 不改库」证明唯一出口覆盖 100%；
2. **`friendUp` 没有 `@Transactional` 却有两条写语句** ⇒ UPDATE 提交后 INSERT 抛错时**库已经被改了**，
   却走 catch 返回 `{success:false}` ⇒ 清缓存必须放在唯一出口**之前**，**绝不能**塞进 `if (updated > 0)` 里。

对照：注解挂在方法上时，**提前 return 也会清**（`goodsAdd` 的图片为空分支即是），placement 与它无关；
这就是 D 笔唯一的精度损失，已用阴性用例测过（提前 return ⇒ 四键仍为 1、写接口 SQL = 0）。

### 5. 负缓存：0 行 → 真 `null` → 被缓存

`userSelect` 是本仓首个负缓存，用于**防 ID 枚举穿透**。两个刻意选择：

- **不做负缓存单独短 TTL**：全局 L2 5m / L1 60s 一把尺，理由与触发条件记在 §9.1。
- **清的是正负条目两者**：新注册的 id 若曾被查过，「不存在」的负条目不清，则本用户到 TTL 前**读不到自己**。

⚠️ 前置条件：`spring.cache.redis.cache-null-values` 必须为 `true`（本仓三处均未设 ⇒ 取 Boot 默认 true）。
若改成 `false`：抛 `IllegalArgumentException`，而**它不是 `DataAccessException`** ⇒ `TwoLevelCache.l2Put`
的降级 catch **不接** ⇒ 穿透防护失效（不是「温和降级」）。

### 6. 逐行异常上抛是**刻意的**行为变更

`friend` 族读方法的原形态是「catch 吞异常 → 返回 null」。照搬进**被缓存的方法**会被**放大**：
某一行 enrich 失败 ⇒ 该好友被静默跳过 ⇒ 这份「少一个人」的列表被**固化到 TTL**（未加缓存时只错这一次请求）。

故读方法**不 catch**：只保留「0 行 → null → 跳过该行」（**业务**事实），技术异常原样上抛，
由 Controller 既有 catch 构造 marker。**代价**：原先「少一个好友的 `success:true`」变成
「整个请求 `success:false`」——**可观测的行为变更**，已登记 §11 ㊴。
这与仓内既有「catch 吞成 marker」的形态**不一致**，属**新模式**，同一节里也登记为「族内不一致」。

### 7. 键用 `#形参名`，不用 `#p0` / `#a0`

`-parameters` 已开，故 `key="#MerchantId"` 可读且改名会被编译期/运行期同时察觉。
代价：形参名成了**契约**（重命名 = 破坏缓存键），已在 Service 里注释说明。

### 8. 复合键模板（由两个实例抽出）

`goodsPrice`（三维）与 `goodsCodes`（二维）抽出可复用的三条：**key 规则 / evict 规则 / 边界**
（边界含「值序未定义」——`SELECT DISTINCT` 无 `ORDER BY`，见 §11 ㊵ 的一维实例）。
**三维键的 evict 只能 `allEntries`**：键含 `GoodName`，而 `goodsUp` 会改 `GoodName` 且其 `WHERE` 是
`(MerchantId, ProductCode)` ⇒ 旧键**构造不出**；精确清会呈现「**条件性正确**」（未改名时对、改名时**静默**漏）。

## 踩过的坑

| 坑 | 教训 |
|---|---|
| **`sync=true` 缺失 ⇒ 击穿防护是死代码** | 不加 `sync` 时 Spring 走 `Cache#get(key)`（两条路各自回落 DB），`TwoLevelCache` 里用于合并并发未命中的 `get(key, Callable)` **根本不会被调用**。实测（冷 L1 + 冷 L2 打 20 并发）：不加 sync → **20 次 DB**；加 → **1 次**。⇒ 「机制已写 ≠ 机制生效」的第一个实例 |
| **`DEL <key>` 只清 L2** | L1 是**进程内** Caffeine（60s），`DEL` 碰不到它 ⇒ `@Cacheable` 在方法体**之前**就拦截了。`friendSelect` 那笔的 V9 首跑**失败**：探针根本没触发，根因就是这个。改「重启 + DEL」得真冷态后才通过 |
| **报告不记缓存状态** | 测量条件无法回溯 ⇒ `66.0` 只能算推断（见「关键数字」第一档） |
| **新 `@Service` 让 `@WebMvcTest` 切片加载失败** | 全部 smoke 用例在**上下文加载期**挂（`No qualifying bean of type … UserCacheService`）。每加一个被缓存的 Service 都要补一个 `@MockitoBean`，本笔累计 4 个 |
| **注解挂 Controller ⇒ Controller 被 CGLIB 代理** | D 笔前 `AopUtils.isAopProxy(controller)=true`。**判据要用 `AopUtils.isAopProxy` + `instanceof Advised`，不是「类名里有没有 `$$SpringCGLIB$$`」**；两条防回归断言留在 `MallManagementApplicationTests` |
| **`@CacheEvict` 不是 `@Repeatable`** | 同一方法上写两个同名注解**不可编译**；`@CacheEvict(cacheNames={A,B})` 只能表达**同精度**多命名空间 ⇒ 混精度（精确 + `allEntries`）**只能 `@Caching`** |
| **「先加 evict 再加读」** | `goodsCodes` / `goodsPrice` 的三条 evict **先于**读接口落地（随 `goodsPrice` 那笔挂上）⇒ 落地前每次写都在清一个**空片**。不是错，但复查时要认得出 |
| `run.sh` 的 `unbound variable` | `A3_DRIVER_JAR` 分支下 `DRIVER_FROM` 无默认值 ⇒ 补默认 |
| Windows 下 `-Dmdep.outputFile` 用 **`;`** 分隔 classpath | `run.sh` 回退分支必须按 `$SEP` 切分，不能写死 `:` |
| `ci.yml` 注释写错 **D3 路径命中的原因** | 真因是 **relocation 重定位**（`mysql:mysql-connector-java` → `com.mysql:mysql-connector-j`），不是「名字相同」。按 glob 找驱动 jar **必然取错版本** |
| 字符集：主机侧手测 / GBK 控制台 / `curl` 传中文 | ① 主机侧手测有字符集坑（`environment.md` 专节）；② Windows GBK 控制台 `print` 中文/`⇒` 抛 `UnicodeEncodeError` ⇒ 写文件用 `encoding="utf-8"`；③ `curl` 传中文在 Windows/GBK 下会**变乱码** ⇒ 探针的入参也会被污染 |

## 元工作教训

A3 那轮记了「**三次无限元工作**」（次要问题 → 深挖 → 引发新一轮工具链问题）。B1 复现的是**同构但更轻**的一种：
**文档漂移链** —— 收尾时修 `cache-map.md §6` 的 +11 坐标，牵出 **4 处**同类问题、写成 **3 笔**：

| # | 发现 | 落地 |
|---|---|---|
| 1 | `§6` 表格坐标 +11 | 与 #2 合并为**一笔**（该笔 amend 过一次，最终 hash `aeaf563`） |
| 2 | 同一句里的「重叠 3 行」是错的（实为 4 行）+ 三个 `G:` 行因读路径搬进 Service 而失效 | 同上（amend 时并入） |
| 3 | 同一份文档的 §1–§5 整节是「引入前」快照却无时效标注 | `c44023c` |
| 4 | 另一份文档的摘要表里「全项目零缓存」+ 同表「测试 6/2」 | `39047b9` |

（**计数口径**：4 处**发现** / 3 个 **commit** —— #1 与 #2 同笔，且该笔 amend 过。列 commit 时若写「四笔」会与
`git log` 对不上。）

**共性**：每次触发都是「**一个次要问题 → 深挖 → 发现同类问题的上一层**」。**根因是坐标/数字被「复制」而非「引用」**
—— 同一事实在多份文档里各存一份，改一处必漏另一处（`cache-layer.md §4` 已留下收敛建议：把重叠行**改为引用**）。

**一条可操作的判据**（本轮真的触发过一次）：**写完一句新话，自查它有没有被同文件里的旧数打脸。**
`project-map.md §5` 那笔我先写了一句「本表逐行反映当前结论」，随即发现**同表**的「测试」行本身就是过期的
（6/2 → 11/4），且恰恰是 B1 期间变的 —— 若不改那一行，我就是在文档里写了一句**假话**。

**另一条**：**不确定的日期必须查，不能猜。** 同一天我在同一个坑里连踩两次：
① `cache-map.md §1–§5` 的快照日，我按「B1 前期某天」猜，实际是**建文件日 2026-09-14**；
② §5「测试」行的旧计数，我按文件建立日猜 09-14，查到实际是 **2026-09-20**（`e3a9ada`）。
两次都是**在写进文档之前**查出来的。

## 与 A3 的关系

**A3 是工具，B1 是应用。** A3 造了 preflight（P0–P7）/ 门禁断言 / JSON 报告 / 负载发生器 /
`--expect-db-host` 这类**测量设施**；B1 是**第一个用它们验业务改动**的轮次。

三条双向影响：

1. **B1 反过来修了 A3 的工具**：`run.sh` 两处（`unbound variable`、Windows classpath 分隔符）、
   `ci.yml` 注释订正。都是「为了跑回归而先修跑回归的工具」—— 属元工作，但产出可复用事实。
2. **B1 暴露了 A3 报告的一个缺口**：报告不记缓存状态（后端状态）⇒ 日后无法回溯测量条件。已登记为待办。
3. **A3 的硬证据在本轮回归中仍然在场**：§0 硬约束让 B1 **不能碰** B-2 的三处 TOCTOU ⇒
   全量并发脚本里 `reproRounds=5/5` 逐轮复现。**这是 B1 最重要的回归断言**：
   加缓存不能把缺陷「治好」成假绿。

⚠️ **口径警告**：**B1 之后 A3 的性能数字不再可比** —— 缓存已启用，`goodstype` 占 S4b 负载 10%
（S1 占 50%），命中缓存后该部分耗时坍缩。**B1 之后若要与 A3 数字对比，必须先声明「缓存已启用」。**
