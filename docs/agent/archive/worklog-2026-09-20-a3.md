## 缺陷记录

### 1. 字符集缺陷（完整记录）

**症状**：`b2run1` 一次运行里，三类 B-2 信号同时「反常」—— `loginAdd` 20 条并发**没有一条**被认成「添加成功」或「已存在」（未判定=20、成功=0）；`goodstype` 已经插出 10–11 行重复数据，却**一条「新增成功」都没有**；`friendAdd` 重复行 10–15，**一条「申请成功」都没有**。看起来像「写入发生了、成功响应全都丢了」。

**旁证异常**：同一次测里的 A 组（S3）从「异常单=0 / PASS」变成「异常单=10 / FAIL」。

**A/B 对照（三个 run，同一脚本、同一台机器，唯一差别是 `-Dfile.encoding`）**：

| 运行 | 与上一次的差别 | 结果 |
| --- | --- | --- |
| `b2run1` | 单文件源码启动（`java scripts/concurrency/ConcurrencyRunner.java`），**不带** `-Dfile.encoding` | 未判定=20 / 成功=0；5 轮全部如此 |
| run 2 `b2run2` | 同上 **+ `-Dfile.encoding=UTF-8`** | 数字自洽：`loginAdd` 1 成功 + 9 撞键→500 + 10 已存在 = 20，三表各轮恰 1 行 |
| run 3 `b2run3` | 去掉 `-Dfile.encoding=UTF-8` | **精确复现 `b2run1`**（5 轮未判定=20、成功=0） → 主因隔离：不是随机、不是环境漂移，是**依赖宿主 JVM 默认字符集** |

宿主字符集实测（`java -XshowSettings:properties -version`）：`file.encoding = GBK` / `native.encoding = GBK`。

**`esc()` 转义对照（决定性一步）**：加一个与终端字符集无关的转义打印，把「源里的字面量」与「响应体」放在同一轮里逐码点比：

```
期望字面量 esc: 添加成功=娣诲姞鎴愬姛   单独0=0
· loginAdd  HTTP 200 body=…（终端乱码）  [esc] 添加成功！
· goodstype HTTP 200 body=…（终端乱码）  [esc] {"msg":"新增成功","success":true}
```

- 源里的字面量 `添加成功` 已被读成 `娣诲姞鎴愬姛`（**5 个汉字变成 6 个乱码码点**，即 UTF-8 字节被按 GBK 解码）
- 服务端返回的是**正确的** `添加成功！`（添加成功！）
- 结论：**响应是对的，判定是坏的**。若无这一行转义对照，终端上两边都是乱码 —— 分不清「响应不对」还是「判定不对」

**机制**：单文件源码启动由启动器**在运行期就地编译**，**不采用任何编译期 `-encoding`**，而按宿主平台默认字符集解读源码。Windows 上 `file.encoding=GBK` → 源里所有中文字面量失真 → 一切依赖中文响应体的断言静默落空。

**根治**（`6ae41d5`，245 insertions）：改成**两步编译** `javac -encoding UTF-8 -d <out>` → `java -cp <out>:<driver>`，并补 `run.sh`。**不采用** `-Dfile.encoding=UTF-8` 兜底 —— 那是掩盖症状，且只在本地有效、对 CI 无意义。

**可追溯**：`charsetSelfCheck()` 每次运行自检（把期望码点写成数字字面量，数字不受字符集影响），并把 `file.encoding` / `native.encoding` / 启动方式 / 自检结果写进日志与 JSON 报告。实测自检行：

```
charset : file.encoding=GBK  native.encoding=GBK  stdout/stderr=强制 UTF-8
          启动方式=两步编译（javac -encoding UTF-8 + java -cp <out>…）  源码字面量自检=PASS
```

即**平台仍是 GBK，但判定不再受影响** —— 与「改平台编码」是两回事。

**复验**：两步编译下全量档（`runId=4f11e708`）23 项门禁断言全 PASS，S3 回到 `异常单=0 / A-S3-2 PASS`；B-2 `reproRounds=5/5`，逐轮数字与修正前**完全一致**（说明受影响的是**判定**，不是缺陷复现本身）。

### 2. 性能退化 = TD-14（`order.OrderId` 无索引）

- `SHOW INDEX` 实测 `order` 只有 `PRIMARY(Id)`；三个 CAS 端点 WHERE 均以 `OrderId = ?` 起头，`EXPLAIN` 实测 `type=ALL`、`possible_keys` 空
- 只读对照（16 线程 × 25，只变行数）：**6 行 p50=1ms → 6006 行 p50=51ms → 12006 行 p50=94ms**（12000 填充行测后已删，`order` 回到 6 行）
- 满负载档（`order` 约 1 万行）：`offered=120 achieved=63.0 QPS wall=114.3s p50=496.1 p95=779.7 p99=842.4 max=1120.6(ms)`
- S4b 长档（60s，从 6 行起）：`achieved=96.2 QPS p50=292.4`，四条门禁断言全 PASS、不变式违反 = 0、5xx = 0
- ⚠️ `achieved` 曾报 68.3 QPS —— 那是**背压之前**的开环负载发生器（无界队列，`achieved` 被算成提交后的排空期均值）。加 `Semaphore` 背压后 68.3 → 63.0 **不是变差、是变准**
- ⚠️ 96.2 vs 63.0 有未排除的混杂因素（全量档里 S4b 非首段，热态方向与本应更快的直觉相反），只能算**同向旁证**
- A3 **不加索引** —— 该缺失正是 A3 要证明的东西

### 3. B-2 三处 TOCTOU（`rounds=5 / reproRounds=5/5`）

- `loginAdd` / `goodstype` / `friendAdd` 三处 check-then-insert 全部复现，两次独立实测逐轮数字一致
- **信号极性不同**：`login` / `user` / `customerimage` 有主键 → 撞键 `ERROR 1062` → **未捕获**（`U:65-105` 无 try/catch，无全局 `@ControllerAdvice`）→ **HTTP 500**（此处 5xx 是「缺陷复现」，**与其它各处相反**）；`goodstype` / `friend` 只有自增主键 → **真的插出重复行**
- 口径：B-2 必须**同时用 JDBC 核对行数**，不能只数「添加成功！」—— TD-15（`loginAdd` 返回「添加成功！」而不插行）会让「只数响应体」失真

## S0 探测与 vmrun 配方

**S0-1 导入**（guest 上）：

```bash
echo 123456 | sudo -S -p '' mysql < /tmp/mall_management_sql.sql
```

- **必须 `sudo`**：guest 上 `root@localhost` 是 `auth_socket`，root 无法用口令走 TCP 登录
- **不需要 `sed` 过滤**：文件自带 `CREATE DATABASE mall_management_sql` + `USE`，与目标库名一致（TD-12）
- ⚠️ 该文件含 **11 条 `DROP TABLE IF EXISTS`** → 只可用于 VM / CI 专用实例

**S0 探测踩过的坑**：

| 坑 | 教训 |
| --- | --- |
| 只看「服务能连上」就以为连的是 8.4 | 驱动 8.0.33 连 8.0.x 也通；必须 `SELECT VERSION()` 看服务端实为 `8.4.11-0ubuntu0.26.04.1` |
| 服务启动日志里找不到 `HikariConfig` 的 `jdbcUrl` | 原以为 Hikari **懒初始化**、配置块只在首次 `getConnection()` 之后才打印 —— **这个判断是错的**（用户指出）：本项目启动期 Hibernate 初始化就会触发连接，故 `HikariConfig` 块在 `Tomcat started` **之前**已打印，**不需要额外请求**。当时记下的错误认知比没记更坏 —— 会让后来者去「补一个请求」而看不出真实原因 |
| 在 `~/.m2/repository` 里按 glob 找驱动 jar | **必然取错版本**：`mysql:mysql-connector-java:8.0.33` 本地只有 `.pom`（jar 因 relocation 落在 `com.mysql:mysql-connector-j`），按 `mysql/mysql-connector-java/*/*.jar` glob 唯一命中的是 **8.0.28**；必须走 Maven 权威解析并校验 jar major=8 |
| 用 `read -r` 捕获 `getGuestIPAddress` | 其输出**含 CRLF**，`\r` 会被并进路径 |
| Git Bash 下 `runProgramInGuest` 一律报「未找到文件」 | 需 `export MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'`（否则 `/bin/sh` 被改写成 Windows 路径） |

**vmrun 通道配方**（将来重做 VM 操作时复用）：

1. `export MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'`
2. **vmrun 不回传 guest 的 stdout** → 把输出落到 guest 文件，再 `CopyFileFromGuestToHost` 取回
3. `getGuestIPAddress` 的输出含 CRLF，不要用 `read -r` 捕获

## 核心收获

1. **判据要能分辨「响应不对」还是「判定不对」**。终端乱码时两者看着一样；`esc()` 把码点打出来，才一步定死是判定坏了。治之前能证明「病在哪」，比治得快重要。
2. **「跑出来不对」不等于「被测对象不对」**。同一个脚本、同一台机器，只因启动方式不同，S3 结论从 PASS 变 FAIL 且不报错 —— 先证明**工具**可信，再谈被测对象（这也是 P0–P7 存在的理由）。
3. **元工作有明确的停手点**：只影响「解释」不影响「结论」的事，写「未逐行取证」就收手。三次元工作都不是因为难，而是因为没有停手判据。
