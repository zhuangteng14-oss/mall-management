## 三、关键方法论

### 1. 先出方案，后写代码

每个任务分三步走：

```
只读探索 → 输出方案 JSON → 确认后写 diff
```

**为什么有效**：
- 一次探索成本约 5–10K token，写错代码要 50–100K token 修
- 方案阶段发现方向错，改一处即可；实现阶段发现方向错，要回滚一堆

### 2. 只读指定文件，禁止整项目重读

每次任务明确列出可读文件清单。

**反例**：

```
请阅读整个项目，然后修 N+1
```

**正例**：

```
只允许读取：
- docs/agent/project-map.md §6
- MallManagementMessage.java:236-370
- MallManagementGoodsController.java:180-210
```

**效果**：输入 token 从 30–80K 降到 5–15K，省 70%+。

### 3. 只输出 unified diff，禁止输出完整文件

明确要求"只输出 patch，不要贴完整文件"。

**为什么**：
- 585 行的 Controller，改 3 行，贴完整文件浪费 580 行
- diff 让人一眼看出改了什么，完整文件要自己找

### 4. 门禁拆两步，不要串在一起

危险操作（`git add .`、`git commit`）单独执行，中间加检查。

**反例**：

```bash
echo "文件数: $(git add --dry-run . | wc -l)"
git add .    # ← 统计结果不会拦截它
```

**正例**：

```bash
# 第一步：只统计
git add --dry-run . | wc -l
git add --dry-run . | grep -c 'node_modules'

# 看结果后手动确认
# 第二步：手动执行 git add .
```

**教训**：Agent 会把"检查"和"执行"写成一条命令，看起来严谨，实际没门禁。

### 5. 单一信息源，禁止文档重复

每件事只在一处写，其他处引用。

| 信息     | 只写在         | 其他处引用               |
| -------- | -------------- | ------------------------ |
| 表结构   | `db-schema.md` | `db-migration.md` 指向它 |
| 技术债   | `tech-debt.md` | context-pack 指向它      |
| 验证步骤 | TD-05 条目内   | TD-09 指向 TD-05         |

**反例**：7 步验证在 TD-05 和 TD-09 各写一份，改一处漏一处。

### 6. 悬空引用必须消除

文档引用了"XX 文件 / YY 章节"，那个东西必须真实存在。

**本次案例**：
- TD-09 引用"TD-05 中的 7 步验证"
- 但 TD-05 里根本没这 7 步（只在对话里）
- Claude 主动拒绝提交，要求先补进 TD-05

**规则**：每次改文档，`grep` 一遍所有交叉引用。

### 7. 事实、建议、决策分三个文档

| 文档                    | 只收     | 例子                  |
| ----------------------- | -------- | --------------------- |
| `db-schema.md`          | 事实     | 表结构、当前 ddl-auto |
| `tech-debt.md`          | 技术建议 | 移除 JPA 依赖、加索引 |
| `business-decisions.md` | 业务裁决 | SettlementDate 语义   |

**为什么**：混在一起会导致——改技术方案要改表结构文档、改表结构要动业务议题、业务议题又引用技术方案，最后互相纠缠。

### 8. 每个 feature 一个会话，做完 /clear

```
feature 完成 → /clear → 新会话用 context-pack 开场
```

**为什么**：
- 长会话的上下文会自然膨胀
- 每次开场读 3 个文件（agent.md + README + pack），不依赖对话历史
- Token 消耗从 30–80K 降到 5–15K

## 四、踩过的坑与修复

### 坑 1：脚本方案在 Windows 上不可靠

- **现象**：`gen-raw.bat` 里的 `tree` 参数错、`findstr` 递归失败
- **修复**：放弃脚本，让 Agent 用自己的文件工具直接读
- **教训**：跨平台脚本坑多，Agent 有文件读取能力就别自己造轮子

### 坑 2：dry-run 统计无门禁

- **现象**：`git add --dry-run | wc -l` 之后直接 `git add .`，统计不拦截
- **修复**：拆两步，看到数字再手动执行

### 坑 3：amend 前忘记 git add

- **现象**：改了 `.gitignore` 但没 stage，amend 后新提交里没有这个改动
- **修复**：amend 前 `git status` 看有没有未 stage 的改动

### 坑 4：凭文件名猜内容

- **现象**：Claude 把 `ImgConfig.java` 描述成"静态资源映射"，实际是 CORS 过滤器
- **修复**：规则 9.1：禁止凭文件名推断，必须读内容

### 坑 5：测试文件误入库

- **现象**：测试上传的图片落进 `static/img/`，进了 `git status`
- **修复**：`git rm --cached` 移除；记录为 TD-08
- **教训**：测试动作要在测试环境做，或在 `.gitignore` 里加白名单

### 坑 6：行号引用随代码变化失效

- **现象**：`tech-debt.md` 里 `U:166` 在代码改后变成 `U:172`
- **修复**：短期改行号；长期引用方法名而非行号

## 五、可复用的"Agent 开发 SOP"

### 阶段 0：初始化（每个项目一次）

```
1. 确认目录结构 → monorepo 还是多仓库
2. 建立 .gitignore
3. git init + baseline-v1
4. 让 Agent 读源码生成 8 份 docs/agent/ 文档
5. 建立 context-packs/ 和 archive/
6. 写 agent.md（规则宪法）
```

### 阶段 1：每个 feature 的开场

```
/clear

你是本项目的开发 Agent。遵守 agent.md。
先执行：
1. 读 agent.md
2. 读 docs/agent/README.md
3. 读 docs/agent/context-packs/<任务>.md
4. git log --oneline -5

按 context-pack 执行，只读它列出的文件。
```

### 阶段 2：每个 feature 的执行

```
1. 只读探索 → 输出方案 JSON
2. 人工确认方案
3. git checkout -b feature/xxx
4. 只输出 unified diff
5. 本地编译 + 运行验证
6. commit（带 scope + self-reviewed）
```

### 阶段 3：每个 feature 的收尾

```
1. review diff（自己看）
2. git checkout main
3. git merge --no-ff feature/xxx
4. 更新 tech-debt / business-decisions
5. 已关闭的 TD 移入 archive/
6. /clear
```

## 六、5 个反直觉点

| 直觉             | 反直觉           | 为什么                   |
| ---------------- | ---------------- | ------------------------ |
| Agent 越自主越好 | 约束越具体越好   | 自主 = 乱跑 = 烧 token   |
| 一次说清楚越好   | 分步骤越细越好   | 大任务容易中途失焦       |
| 让它自己检查     | 必须有人工门禁   | Agent 会"看着自己觉得对" |
| 输出越详细越好   | 只输出 diff 最好 | 完整文件浪费 token       |
| 一个会话做到底   | 做完就 /clear    | 长会话质量下降且贵       |

1. `agent.md` —— 规则模板
