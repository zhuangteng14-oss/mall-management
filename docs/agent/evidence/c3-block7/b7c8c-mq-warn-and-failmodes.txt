块 7 · commit 8c —— MQ 探测日志的两种失败模式 + 周期性 WARN（实测记录）
时间：2026-10-14 21:07 – 22:33（+08:00）
被测：RabbitEventPublisher 的探测线程（每 5 秒实测一次 broker）与它的记日志口径

────────────────────────────────────────────────────────────────────────
一、这次要修的是什么（起因：一次实测打脸，不是设计推演）
────────────────────────────────────────────────────────────────────────
原实现**只在状态翻转时**记日志：`connected` 初值 false，探测每轮仍 false 时
`now == was` 恒成立 ⇒ **一个字都不记**。

实测对照（旧代码，`_work/b7c8c-boot-unreach.log`，21:16 那次，host 指向一台没有
broker 的机器）：
  · 应用**照常启动** —— `Started MallManagementApplication in 24.052 seconds`
  · 整份日志（50010 字节）里含 `[EVENT]` 的行：**0 条**（grep -c 实测）
  · 日志里串起来的是 Spring AMQP 自己的重连栈：
    `AmqpIOException: java.net.SocketTimeoutException: Connect timed out` 反复出现
⇒ 「broker 不可达 ⇒ 探针记一条 WARN」这个说法在**那次**不成立。而「一直不通」
恰恰是最该被看见的场景（host 配错、broker 没起）。

修复：失败记两档 —— 翻转必记（原行为不动）+ 稳态按
`mall.observe.mq.warn-interval-ms`（默认 300000ms = 5 分钟）重复记；
「首条」不受节流（启动即不可达时立刻有声音）。

────────────────────────────────────────────────────────────────────────
二、判据 ②：MQ 从「通」到「断」，翻转 WARN 仍在（原行为不变）✅
────────────────────────────────────────────────────────────────────────
出处：`_work/b7c8c-warnrun2.log`（22:18:51 起，dev profile；为制造可控的「断」，
后端连的是本机 TCP 转发 `127.0.0.1:5672` → VM 的 5672，杀转发器 = 对应用而言 broker
不可达；全程未动 VM 上的 rabbitmq 服务）
  22:18:51.082  INFO  MQ 已连接            ← 起手就连上（false→true 翻转）
  22:19:41.164  WARN  MQ 不可达（刚从「已连接」掉下来）   ← 杀转发器后 5 秒内
⇒ 翻转 WARN 照记，文案能区分「翻转」与「稳态重复」。

────────────────────────────────────────────────────────────────────────
三、判据 ①：MQ 断 10 分钟后，至少 2 条周期性 WARN ✅（实测 2 条）
────────────────────────────────────────────────────────────────────────
同一条日志的后半段（转发器一直没起回来）：

  22:19:41.164  WARN  MQ 不可达（刚从「已连接」掉下来）   ← 翻转那条（起点）
  22:24:42.318  WARN  MQ 不可达（仍未恢复，按间隔重复）   ← 周期 #1（+5 分 1.2 秒）
  22:29:43.268  WARN  MQ 不可达（仍未恢复，按间隔重复）   ← 周期 #2（+5 分 1.0 秒）

  ⇒ 10 分钟窗口内周期 WARN = **2 条**（判据要求 ≥2）；周期间隔 5 分 0.9~1.2 秒，
    与默认 300000ms 相符（探测本身每 5 秒一轮，故允许 ≤5 秒的取整误差）。

四、顺带验到的一条：恢复重连也照记（同一份日志继续）
  22:31:28.579  INFO  MQ 已连接            ← 转发器起回后，false→true 翻转
  合计 5 条 [EVENT]：已连接 2（22:18:51 / 22:31:28）+ 不可达 3（1 翻转 + 2 周期）

────────────────────────────────────────────────────────────────────────
六、另一种失败模式（不是本笔的修复对象，但必须一起记，因为两者行为不同）
────────────────────────────────────────────────────────────────────────
**broker 在、但凭据认不上** ⇒ 应用**起不来**（`_work/b7c8c-boot-nomq.log`，21:11 那次，
把 password 置空起）：
  ApplicationContextException: Failed to start bean
    'org.springframework.amqp.rabbit.config.internalRabbitListenerEndpointRegistry'
    ← FatalListenerStartupException: Authentication failure
    ← AmqpAuthenticationException: com.rabbitmq.client.AuthenticationFailureException:
      ACCESS_REFUSED - Login was refused using authentication mechanism PLAIN
处置（8c 内已改）：消费者 `ObservedEventConsumer` 加 `@ConditionalOnProperty
(prefix = "spring.rabbitmq", name = "host")` ⇒ a3 不配 host ⇒ 该 bean 不存在 ⇒
CI 里那格 rabbitmq service 不会把启动变红；发布侧仍无条件注册（它的失败路径
就只是本文件记的「探针 WARN + 页面黄点」）。

────────────────────────────────────────────────────────────────────────
七、取证口径备注
────────────────────────────────────────────────────────────────────────
· 日志文件的编码是 **GBK**（Windows 上 maven 控制台的默认口径），不是 UTF-8：
  按 UTF-8 硬读会得到替换字符，`MQ 已连接` 一个都匹配不上。本文的中文抽取走
  `_work/b7c8c-warn-extract.py`（先 utf-8、失败退 gbk，输出一律 UTF-8）。
· 未加针对周期 WARN 的单测：判据本来是「日志取证」，而单测要验它得把时钟抽成
  注入点（放大改动面）。本文件的三条实测即本笔该项的验收。
· 本文件刻意不写「文件:行号」形式的引用（那会被本仓的 refs 扫描当成真引用）。
