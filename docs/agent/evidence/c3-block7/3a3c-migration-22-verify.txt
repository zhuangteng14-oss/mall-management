═══════════════════════════════════════════════════════════════════════
上面 1–11 条只能证明「MySQL 收下了这两列」（DDL 层）；第 12 条能读到真值，是因为
中间跑了一次**真实的链路**。把这条链路的每一环记在这里，便于复核：

  ① 后端重启为**新代码**（`./mvnw spring-boot:run -Dspring-boot.run.profiles=dev`，
     PID 23424，`Started MallManagementApplication in 8.156 seconds`）。
     旧进程（PID 31868，00:38 启的）已按端口强杀 —— 它跑的是**第一步**的类，
     没有 RemainingStock / FieldsJson 的携带代码 ⇒ **不重启则第 12 条永远是 null**。
     ⚠️ 口令从 `_work/mq-pass` 读进环境变量注入（**未回显**）；不注入 = RabbitMQ
     ACCESS_REFUSED = 整台起不来（第一次重启就栽在这里，日志在 `_work/3a3/backend-boot-live2.txt`）。
  ② 发一单真实请求（HTTP 200，`{"msg":"订单添加成功","success":true}`）：
     `POST http://localhost:8088/order/orderAdd`
     参数：`CustomerId=B7CAPC-sgu0g` / `MerchantId=B7CAPM-sgu0g` /
     `OrderId=PROBE3A3B-20261017-01`（**每次要换**：撞唯一键会走「订单已存在」早退分支，
     根本不扣）/ `Price=1` / `Quantity=1` / `PayIf` `DeliveryIf` `ReceiveIf` = 0 /
     `Items=[{"code":"SEED-GD-104-7045","name":"probe","price":1,"qty":1}]`。
     ⚠️ 明细刻意走**显式 `Items`**（JSON）而不是 `ProductInformation` 回落口径 —— 前者的
     `code` 是逐字给定的；后者靠反推，验证时不该把两件事混在一起。
     ⚠️ 参数值全 ASCII：Windows/GBK 下 curl 传中文会变乱码（本仓记过这个坑）。
  ③ 扣减真的发生了：`goods_sku` 里 `SEED-GD-104-7045` 的 `Stock` 由 **60 → 59**。
  ④ 事件经 `StockMetrics.deduct(...)` → 广播器 → 发布方 → RabbitMQ → 消费者 →
     台账落库，**1 秒内**可读；第 12 条那个 `Id = 553152` 就是它。
     `RemainingStock = 59` 与第 ③ 步的读回值**一致** ⇒ 「当时剩余」取的是**扣完之后**的值，
     不是扣之前、也不是事后回查的当前值。
     `FieldsJson` 被 MySQL 的 `json` 列**接受并读回**（读回来还是 JSON 对象，不是字符串）
     ⇒ 落进去的是合法 JSON，`ObservedEventDao` 那段序列化是对的。
  ⑤ ⚠️ **一分钟后它会变**（复核时务必知道这条，否则会以为记录写错了）：
     本单没有支付，**超时取消 job** 于 01:12:54 把它回补了 ⇒ 现在再读 `goods_sku` 是 **60**
     （不是 59）。第 ③ 步的 59 是**当时**的快照。这条回补本身也是**正面证据**：
     回补那次事件（`Id = 553153`，title=库存释放）的 `RemainingStock` 是 **null**，
