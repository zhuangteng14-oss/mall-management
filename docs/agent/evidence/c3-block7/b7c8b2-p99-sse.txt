块 7 · commit 8b2〈指标 P99 剔除 SSE 长连接〉—— 实测证据（2026-10-14，dev profile + VM 库）
================================================================================

现象（用户三页截图反馈）
--------------------------------------------------------------------------------
指标面板 P99 = 26,843.546 ms 标红 + 判据条「P99 26843.546ms（≥ 1000ms）」。
用户原判：「无数据时的默认值（没有请求，Micrometer 走默认）」。
⇒ **实测不成立**，真机制见下。

真机制（actuator http.server.requests 按 uri 拆，2026-10-14 dev 8088）
--------------------------------------------------------------------------------
  /admin/observe/metrics/stream    6 次 / 109.07 s  → 均摊 18.2 s
  /admin/observe/events/stream     4 次 /  51.62 s  → 均摊 12.9 s
  /admin/observe/orders/stream     3 次 /  20.33 s  → 均摊  6.8 s
  /admin/observe/attack/run        1 次 /  13.06 s
  /order/orderAdd（真业务）     1654 次 /  73.13 s  → 均摊 44 ms
⇒ 13 条 SSE 长连接贡献约 **181 s** 的「耗时」，而 1654 条真业务请求拢共才 73 s。
   SSE 的「耗时」是**连接存活时长**（客户端挂多久），不是一次请求的处理时长；
   它被 Micrometer 的衰减窗口抬进分位 ⇒ P99 报 26.8 s ⇒ 健康度误判成红。

修法（A + B，两段，都在 MetricsSnapshotService 一个文件）
--------------------------------------------------------------------------------
A · 延迟聚合剔除 SSE：meanMs / p95Ms / p99Ms / maxMs 只聚 **uri 不以 `/stream` 结尾** 的序列；
    count / qps / errors4xx / errors5xx **仍算全量**（SSE 也是真请求，只是其耗时不是延迟）。
    （判据字面量与既有 `shared/web/TraceLog.SKIP_SUFFIX = "/stream"` 相同 —— 两处同一口径。）
B · 本拍无延迟样本 ⇒ p95Ms / p99Ms / meanMs / maxMs 一律 **null**（页面据此显 "—"）。
    ⚠️ 单靠 B 修不掉截图那个红：那一拍 `count=1`、`qps≠0`（见下面 seq 0 的实测）。
    前端 MetricsPanel.vue 本来就是 `p99 === null ? '—'` ⇒ **前端零改动**。
