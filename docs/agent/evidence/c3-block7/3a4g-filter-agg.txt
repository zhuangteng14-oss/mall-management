二、根因（三处，缺一不可）
-------------------------
1) 统计与列表不同源（主因）
   统计一直读 RAW（压缩前、上限 8192）；③ 列表的筛选链却从 W.events（上限 200）
   出发。WARN 一旦被后续 INFO 挤出 200 条窗口，列表按 ≥WARN 过滤必然得到 0 条，
   与统计面板的数字无关。用户要求的顺序（先筛 RAW → 再聚合 → 再窗口化）此前
   从未落在这条链上。

2) computed 引用不更新（隐藏原因）
   改造过程中 `ranged` 直接返回 RAW 的普通数组。RAW 是原地追加、非响应式；
   每次重算返回**同一个数组引用**，Vue 的 computed 认为值没变，不会通知下游
   `filtered` / 列表。表现是 rawWindow 已更新、列表永远停在首帧的空数组。
   修法：`ranged` 每次返回新数组（展示链改用单趟扫描 RAW，见下）。

3) 虚拟滚动游标残留（用户指出的索引问题）
   筛选把行数从几百缩到几十时，vStart 仍是按旧行数算的值；`slice(旧起点, 旧终点)`
   会切出空数组。实测把 vStart 推到 9999 时旧实现会得到 0 行。
   修法：
   · 筛选条件（类 / 严重度 / ≥WARN / 对象 / 搜索 / 时间范围 / 聚合开关）一变，
     同步把 vStart 归零、vEnd 置 40；下一帧（rAF）把 scrollTop 拉回 0 并重算窗口；
   · vRows / updateWindow 在切取前把游标夹到 [0, n-1]，即便某一帧还没重算，
     非空列表也至少切得到一行；
   · 程序性 scrollTop=0 产生的那次 scroll 事件用一次性标记吞掉，避免被 onScroll
     误判成「用户上滚」而进入 frozen（那会让列表停止并入新事件）。


三、修复（EventLog.vue）
------------------------
1) 筛选链改为单趟扫描 RAW：
   for (const e of RAW[cur].events) { 时间范围 → 类 → 严重度 → ≥WARN → 对象 → 搜索 }
   ⇒ 返回新的 filtered 数组；不再先复制 ranged 再 filter。
2) streamRows 的固定顺序：
   filtered（RAW 原始行）→ 聚合（开关开启时）→ 排序（时间正序）→ vRows 窗口化。
   聚合关闭时，从筛完的 RAW 里按 ts/seq 取最新 200 条逐条显示（数据侧上限）；
   聚合开启时一行代表 N 条，不截断 —— 列表可覆盖整本 RAW，与统计同源同量。
3) 空状态判据改为 filteredRaw 是否为空：
   · 本会话有原始事件、筛选后 0 条 ⇒「当前筛选下一条也没有」；
   · 真一条原始事件都没有 ⇒「本会话还没收到任何事件」。
   （旧实现用 events.length 判，时间范围把行全排掉时会误报。）
4) aggregateEvents 不再为每个成员维护 seqs 数组：聚合行不进 W.events，
   该数组已无消费方；每拍为几千条事件 push seq 只是白付分配成本，已删除。
   forgetSeqs 相应简化为「删除单条 seq」。
