# C3 功能模块设计意图

> 来源：2026-10-08 与用户的多轮讨论整理。
> 到 C3 各笔时直接读本文件。
> 本文件定义「做什么」，不定义「怎么做」（那归各笔的方案）。

## 零、定位

C3 是**平台方管理端**，不是「数据查看器」，也不是「超级商家」。

管理员不是普通用户的放大版，是**拥有平台方独有权力**的角色。
这些权力普通用户和商家**永远不该有**。

**核心判断**：
- 普通角色做「自己那部分」
- 管理员做「平台方治理」——审核 / 模板 / 介入 / 举报 / 通知

## 二、业务域逐块

### 1. 用户与商家治理

| 视图 | 管理员独有动作 |
|---|---|
| 用户列表 / 详情 / 行为 | 封禁 / 解封 |
| 商家列表 / 资质 | 入驻审核（通过 / 驳回） |
| 举报工单 | 处理 / 归档 |
| 标签 | 分组 / 打标 |

### 2. 商品与类目治理

| 视图 | 管理员独有动作 |
|---|---|
| 商品列表 | 上架审核（商家提审 → 通过/驳回） |
| 类目树 | 类目增删改 |
| **基础模板库** | **详情 / 规格 / 售后模板的维护**（商家选用） |
| 违规商品 | 下架 / 删除 |

### 3. 订单治理

| 视图 | 管理员独有动作 |

| 全量订单（按用户 / 商家 / 状态 / 时间筛） | 介入改状态 |
| 异常监控（超时 / 纠纷 / 退款） | 强制退款 / 强制完成 |
| 操作日志 | 通知双方（站内信 / 系统消息） |

### 4. 营销运营

| 视图 | 管理员独有动作 |
|---|---|
| 券效果数据 | **优惠券创建 + 发放** |
| 活动效果 | **国补规则** |
| 商家折扣 | **折扣模板**（供商家选用） |
| 秒杀 | **邀请 + 审核**（**双向制**：管理端不能单向指定 —— 见 §9.1） |

⚠️ **秒杀演示挂攻击模拟器下，但秒杀活动的管理挂这里。**

### 5. 消息与内容治理

| 视图 | 管理员独有动作 |
|---|---|
| 消息列表 | 违规消息处理 |
| 评价列表 | 审核 / 删除 |
| 评论列表（**多对象**：商品 / 用户 / 楼中楼） | 审核 / 删除（见 §9.2） |
| 举报中心 | 处理（用户举报商家 / 商品 / 消息） |

### 6. 系统通知

| 视图 | 管理员独有动作 |
|---|---|
| 通知历史 | 平台公告（对全站） |
| | 系统通知（对用户 / 商家群发或定向） |

## 三、可观测域逐块

### 7. 攻击模拟器

**设计档已有**（用户单独提供），按那份落地。⚠️ **profile 用 `dev`（或未来的 `sim`），不用 `a3`** —— 复用的是 A3 的并发脚本**框架**（`scripts/concurrency/`），不是它的 profile；`a3` 的 job 全关（压测确定性），拿它跑演示会**什么都看不到**（见 `tech-debt.md` **TD-35**）。**落笔时写进本块的 context pack**。

### 8. 指标面板

**不要 8 根折线**。做「系统血管图」：
- 大数字 + 趋势箭头（缓存命中率、锁竞争）
- QPS 面积图（实时推流）
- 锁热点热力图

### 9. 状态流转

**订单生命线**：
- 状态机画成图（节点 + 箭头）
- 每单一条进度条（待付款 → 待发货 → 待收货 → 已完成）
- 管理员介入路径高亮

### 10. 实时日志

**事件流卡片**（不是纯文本刷屏）：
- 每条 = 图标 + 时间 + 标题 + 详情
- 按严重度着色
- 可点击展开

### 11. 权限与审计

**横切所有写操作**：
- 记录：谁 / 何时 / 对象 / 改前 / 改后
- 查看：可筛选 / 可导出

## 四、引用关系

```
用户与商家治理 ──┐
                 │
商品与类目治理 ──┤
                 ├──→ 审计（权限与审计记录）
订单治理 ────────┤
                 │
营销运营 ────────┤
                 │
消息与内容治理 ──┤
                 │
系统通知 ────────┘

商品 ──→ 订单 ──→ 状态流转
           │
           └──→ 指标 / 日志

攻击模拟器 ──打──→ 业务域 API ──→ 状态/指标/日志/审计 全联动
```

**关键链**：
- **订单治理是枢纽**——读用户/商品、连营销、产状态流转
- **审计横切全部**——每一块写操作都落审计
- **攻击模拟器是演示引擎**——一跑，可观测域四块全活

## 五、可观测域视觉化原则

**核心：把「数据」变成「驾驶舱」。**

三个转换：
- **数字 → 状态**（健康/告警/异常，一眼可辨）
- **表格 → 叙事**（一条订单从生到死，走一遍）
- **静态 → 联动**（一个动作，多处响应）

**三招**：
1. **健康度打分**——一个大数 + 颜色，不用看图
2. **故事线视图**——一条时间线讲完一单
3. **异常高亮 + 一键跳转**——不让你找，直接给

**布局**：
```
┌────────────────────────────────────────┐
│ 顶部状态条：● 健康  QPS 1.2k  P99 45ms │
├──────────────┬─────────────────────────┤
│              │                         │
│  主视图区     │   事件流（右侧栏）        │
│  （可切换）   │   实时滚动               │
│              │                         │
└──────────────┴─────────────────────────┘
```

### 5.1 子项页含多块 ⇒ 页内 tab，tab 数 2–4 个（2026-10-09 用户裁决）

**规则**：一个**子项页**（侧边栏二级项对应的一页）里如果装了**多块**内容，用**页内 tab** 切分，
**不**往下再增一层侧边栏、**也**不拆成多个地址。

**判据（什么时候才该拆出去）**：这些块**是不是同一个域** —— 即「回答同一个问题」。
  · **同域** ⇒ 留在一页、页内 tab。例：「用户与商家治理」的三块（入驻审核 / 用户治理 / 降级控制）
    回答的都是「**这个账号现在是什么身份、能不能继续当**」⇒ 一页三 tab。
    ⚠️ 拆成三个地址的代价是**具体的**：管理员要在三个地址之间来回跳，而这三件事天然连着做
    （查到这个账号在降级 → 顺手就去看它的入驻记录）。
  · **不同域** ⇒ 拆成**侧边栏顶层独立项**（`subs: []`，与「概览」同形 —— **层级不增深**）。
    例：管理员收件箱 回答的是「**有什么待办在等我**」，不是「治理某个账号」⇒ 从
    `AccountsPage.vue` 的页内第 ④ 块提成 `/admin/inbox`。（来源：「用户与商家治理」页页内**四块**
    靠滚动区分，用户 2026-10-09 手验后裁决**甲案**。）

**条数**：**2–4 个**。1 个 = 没有切的必要；5 个以上 = 说明这个子项页其实装了两个域，回去重新分。

**样式**：**一套**（不许各页自造）。基准 = `AccountsPage.vue` 的 `.a-tabs` / `.a-tab` / `.a-tabn`：
下划线选中态（`border-bottom: 2px solid var(--brand-ink)`）、未选中走 `--ink-3`、tab 名后带一个
小号计数（`note()`）。⚠️ 选中态**用下划线**，不用「左侧强调条」—— 那条是 `tokens.css` 的房规禁区。

**副作用（必须一起做，否则「点了没反应」）**：tab 里的按钮若要跳到另一个 tab
（例：用户行上的「降级操作」要跳到降级表单），**必须同时切 `tab` 值** —— 见
`AccountsPage.vue` 的 `pickDowngrade`。

## 六、答辩演示线

```
1. 打开攻击模拟器 → 点「跑混合压力」
2. 切到状态流转 → 看订单实时流转
3. 切到指标面板 → 看 QPS / 命中率曲线
4. 切到实时日志 → 看日志刷屏
5. 切到权限与审计 → 看这次演示被记录
```

**一条线串五块，这是可观测域的价值。**

**答辩台词**：
> 「我现在打一波混合流量，你看——指标在涨，订单在流转，日志在滚，这次演练被记录了。」

## 九、业务修正（2026-10-08 用户裁决 —— **覆盖 §二 / §八 里相冲突的行**）

### 9.1 秒杀：双向制（管理端只能「邀请」+「审核」，**不能单向指定**）

**作废**：§二 第 4 块「营销运营」表里的秒杀一行 —— 原写「秒杀活动设置（时间 / 商品 / 数量）」，
口吻是**管理端单向指定**。（该行已就地标注，见 §二。）

只剩两条路径，且发起方与决定方**相反**：

| 路径 | 谁发起 | 谁决定 | 落表 |
|---|---|---|---|
| **A** 管理端**邀请**商家 | 管理员 | **商家**同意 / 拒绝 | `seckill_invitation` |
| **B** 商家**申请** | 商家 | **管理员**审核 | `seckill_application` |
| ~~C 管理端单向指定~~ | ~~管理员~~ | ~~——~~ | **❌ 不做** |

**表（两张，镜子关系；刻意不合成一张）**：

- `seckill_invitation` —— A 路径：管理端发出邀请 + 商家应答。
- `seckill_application` —— B 路径：商家提出申请 + 管理端审核。

> 为什么不合成一张：两条路径的**发起方 / 决定方 / 状态机方向**相反，
> 合成一张得靠一个 `direction` 列在状态机里到处分叉 —— 两张表更直。

### 9.2 评论区：多对象（三种对象 + 楼中楼 + 问答式 + @ + 站内通知）

**作废**：§八「C3 边界」的「不做评论区（C3 后）」。**评论区进 C3**，归第 6 块「内容+消息块」。
（该行已就地标注，见 §八。）

**对象三种**（由 `targetType` + `targetId` 两列表达）：

| `targetType` | 对象 | 例 |
|---|---|---|
| 商品 | 商品评论 | 买家评商品 |
| 用户 | 用户留言 | 给某人留言 |
| 评论 | 对评论的回复 | 楼中楼 / 问答式 |

**形态**：

- **楼中楼** —— `parentId` 指向父评论（自引用）。
- **问答式** —— 楼主提问 / 他人回答；形态上仍是「回复某条评论」，故**共用同一个 `parentId`**。
- **`@` 提及** —— `comment_mention` 表记录提及关系。
- **站内通知** —— 「被评论 / 被回复 / 被 @」要能触达当事人。

**表（两张）**：

- `comment` —— 评论本体：`targetType` + `targetId`（对象）+ `parentId`（楼中楼）。
- `comment_mention` —— `@` 提及关系。

> ⚠️ **对批 1（基础设施）的影响**：**I2「系统通知」需支持「被评论 / 被回复 / 被 @」三类事件**
> —— 见 `docs/agent/context-packs/c3-block-1-infra.md` 的「要新建」。
