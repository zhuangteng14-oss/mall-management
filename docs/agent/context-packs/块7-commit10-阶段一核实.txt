1. 件 3 · 状态流转两处动画

【3a 订单行进度条的「—」不流动】

现状
  · 进度条是**纯 DOM，不是 SVG**：<span class="a-of-track"> 里 4 个
    <i class="a-of-node">（节点）+ 3 个 <i class="a-of-seg">（就是「—」）。
    （OrderFlow.vue 模板 :104-109）
  · .a-of-seg { flex:1; height:2px; background: var(--line-2) }
    .a-of-seg.on { background: var(--success) }
    （OrderFlow.vue:795-802）—— **只有颜色切换，没有任何 animation / transition**。

为什么不符
  · 稿要「—」流动（虚线推移），现在是静态实线靠变色表示已走过。
  · 核实清单④的答案：**是 CSS/DOM，不是 SVG** ⇒ 用户原话给的两条改法里
    「SVG 虚线 stroke-dashoffset」这条不适用（没有 SVG 可改）；
    要么给 .a-of-seg 加 repeating-linear-gradient + background-position 动画，
    要么把这一段整体改成 SVG 虚线。

「只在活跃订单上流动」怎么落地（现成判据）
  · 模板里已经有 r.cancelled（且已有 .is-dead 类把整条压暗）
  · r.step（0..4）：补一条「step === 4（已完成）也不流动」即可。

【3b 状态机图全程不动 —— 已实测坐实，两个互相独立的原因】

实测方法（按用户要求做了一次真跑）
  · 起一轮真实攻击：orderBurst 100%，20 并发 20 秒（AttackEngine 真跑）。
  · 同时用 curl 挂住两条 SSE 流抓帧：
      /admin/observe/orders/stream  → 683 KB / 28 帧
      /admin/observe/events/stream  → 1.7 MB / 18 帧
  · 产物：_work/p3b-orders.sse、_work/p3b-events.sse、
          _work/p3b-attack.json、_work/p3b-analyze.py（均在 gitignore 的 _work/）

实测结果（orders 流）
  · moves **有**数据 —— 28 帧里 17 帧非空，共 **4670 条**
    （moveCount 峰值 344）。⇒ 驱动源（SSE order 流的 moves）是**接上的**，
    不是「没接到」。
  · 但 4670 条**逐条统计**的结果是：
        from 取值分布   = {None: 4670}        ← 100% 为 null
        to   取值分布   = {CREATED: 4670}     ← 100% 同一个值
        action 分布     = {create: 4670}
        result 分布     = {applied: 4670}
        唯一 (from,to) 组合 = [(None, 'CREATED')]   ← 只有一种
    样本：{"orderId":"SIM-BURST-12187-763","action":"create","from":null,
           "to":"CREATED","result":"applied","ts":1791994213554}

原因一 · 守卫条件把建档挡在门外
  · OrderFlow.vue:498 是：
        if (m.from && m.to) {
          flash(activeEdges, `${m.from}>${m.to}`)
          flash(pulseNodes, m.to)
        }
  · from 为 null ⇒ 整个 flash **被跳过**。攻击演练产生的流转 100% 是建档
    （action=create、from=null），所以**一次边高亮、一次节点脉冲都不会发**。

原因二 · 前后端命名空间错配（就算 from 非 null 也白搭）
  · 后端 moves.from/to 用的是 **OrderState 枚举名**：
      CREATED / PAID / SHIPPED / RECEIVED_NODELIVERY / ILLEGAL_* …
      （order/model/OrderState.java:44-72）
    生成路径可复核：OrderTransitionRecorder.applied() 里
      toState = stateMachine.stateName(payIf, deliveryIf, receiveIf)
      → metrics.transition(action, fromState, toState, ...)
      → MallOrderStateMetrics.event(...) → 进 SSE 的 moves
      （OrderTransitionRecorder.java:113-118；MallOrderStateMetrics.java:150-154）
    实测到的 "to":"CREATED" 正是 stateName(0,0,0) 的返回值。
  · 前端 MAIN_EDGES 的 id 用的是 **DB 派生五态 code**：
      waitPay>waitShip / waitShip>waitReceive / waitReceive>completed
      （OrderFlow.vue:292-296），节点 key 同理（:284-290）
      取消两条：waitPay>cancelled / waitShip>cancelled（:298-299）
  · 两套名字**没有一个对得上**：
      CREATED ≠ waitPay · PAID ≠ waitShip · SHIPPED ≠ waitReceive
      COMPLETED ≠ completed（大小写也不同）
  · ⇒ 即便演示时人工点一次「付款」，拼出的 ${from}>${to} = "CREATED>PAID"
    在 MAIN_EDGES 里查不到；pulseNodes 拿到 "PAID"，也不在 FSM_NODES 的
    key 集合里。**两条路都亮不了。**

结论
  · commit 7 报告里「走过的边亮绿 1.2 秒、落到的节点脉冲」这句，
    在两条路径上都不成立：建档被守卫挡掉、真流转被命名空间挡掉。
  · 动画的**机制件全都在**（flash() :355、FLASH_MS = 1200 :269、
    .is-pulse / @keyframes a-of-node-glow :882、a-of-node-pulse :822），
    **是把数据喂进去的那一层断了**。这也解释了为什么「看起来像是做了、
    跑起来一点不动」—— 代码读起来是对的，只有实测才露馅。

改动面估算（3a + 3b 合计）
  · OrderFlow.vue 单文件，约 **120 ~ 180 行**
      - 新增 OrderState ↔ 五态的映射表                    ~20 行
      - 改 absorbMoves（守卫条件 + 映射）                  ~15 行
      - .a-of-seg 流动 CSS                                ~15 行
      - 节点角标（每状态多少单）模板 + 样式                 ~40 行
      - 若改为 SVG 虚线：模板 :104-109 那段重写            ~25 行
  · 后端：**不用改**（moves 已在推 from/to/action/result/ts）

不确定点（3）
  ① 「节点角标 = 每状态多少单」可以直接吃帧里的 counts
     （cancelled/completed/waitReceive/waitShip/waitPay/total，实测帧里都有），
     不用新后端。但它是**全表**口径（OrderDao.countOrderStates() 无时间窗）
     —— 演练时会显示 11558 这种总量，不是「本批次」。要不要改成本批次口径
     = 需要新的后端查询；本笔不动后端的话，只能显示全表。
  ② 「边高亮 1.2 秒」在高频演练下会被**反复重置**（4670 条 moves / 20 秒
     ⇒ 每秒 200+ 次 flash 同一 key），实际观感是「常量高亮」，

现状（逐条对用户核实清单）

     而 EventLog.vue 现在是**自己从客户端那个 1000 条上限的列表里现算**
     kind/severity 计数（:356 / :361）—— 用的是**被截断过的客户端缓冲**，

     ⇒ **件 2 数据面零后端改动**，全部前端可做。

不确定点（2）
  ① **两条 events 流并存会耦合**：EventStreamService.sentSeq 是**单例字段**
     （:55），frame() 是 synchronized（:75）；两条流共享 sentSeq，也共享
     同一个 FramePacer。机制上后一条流会走 pacer.reuse() 拿到**前一条流
     刚产的那一帧**（含同一批 events），所以事件**不会系统性丢失**，
     但两条流的「本拍」是同一拍、帧号互串。
     ⇒ 件 1 若在攻击页也开一条 events 流（做日志迷你块），
       **必须实测**「攻击页 + 日志页同开，两边事件条数是否一致」。
       建议在 10c 落地时用探针验一次，别拍脑袋。
  ② 稿里「暂停」在 SSE 语义下 = 客户端停止 append（服务端照推），
     **不是**真的暂停采集。且 EventBroadcaster.poll() 只由流线程驱动
     ⇒ 如果为了「暂停」把流关掉，**台账就不落库了**
     （tech-debt TD-61 那条）。要定口径：暂停 = 只停渲染、连接不断。
