一、Q1 核实 · 攻击引擎的并发模型
=====================================================================

【1.1 现状：逐行读出来的模型】

入口：AttackController#run (:114-132) → DrillRecordService#run (:81-112)
      → AttackEngine#run (:364-418) → runPhase (:421-471)

runPhase 的做法（:424-456）：
  ① List<String> plan = threadPlan(chosen, concurrency);   ← 排 N 条线程
  ② long deadline = now + seconds;
  ③ for (String key : plan) { new Thread(...).start(); }     ← N 条守护线程
  ④ 每条线程的循环体（:441-445）：
        do {
            meter.add(fireOnce(key, target, baseUrl, seq.getAndIncrement(), ...));
        } while (!oneshot && System.nanoTime() < deadline && !interrupted);

⇒ **模型 = 「N 条线程各自满速死循环，跑到截止时刻」**。
   · **没有任何节流器 / 令牌桶 / sleep / RateLimiter**（全文件 grep 无 parkNanos/sleep/Timer）。
   · 所以「并发数」是**唯一**的速率旋钮，实际 QPS = Σ(1 / 单请求耗时)，**不可控**。
   · `threadPlan` (:848-888) 把 concurrency 按权重分给场景（每场景保底 1 条线程）。

【1.2 实测吞吐（本次两轮攻击的第一手数字）】
   · 第 1 轮 probe3b：20 并发 × 25 秒 ⇒ TotalRequests 10057 ⇒ **约 402 QPS**
   · 第 2 轮 p3b    ：20 并发 × 20 秒 ⇒ TotalRequests 10138 ⇒ **约 507 QPS**
   · ⇒ 单线程能力约 **20-25 QPS**（单请求约 40-50 ms，引擎与后端同机）。
   · 缺省 concurrency = 100 ⇒ 缺省一轮 60 秒约 **5 万请求量级**
     （这是外推，不是实测 —— 标注为「推断」档）。

【1.3 ⚠️ 必须先说清的一件事：120 QPS 打不崩】
   用户口径是「按 120qps 打入，连着打 60 秒（会不会崩？）」。
   实测单线程 20-25 QPS ⇒ **6 条线程就能打满 120 QPS**（现引擎缺省 100 条）。
   ⇒ 按当前后端能力，**120 QPS × 60 秒 = 7200 请求，几乎不可能崩**。
   建议在演示口径上如实处理，别让「跑完了、没崩」被读成「引擎没使劲」：
   · 结果里报**实际达成的 QPS**（total / duration），而不是只报目标值；
   · 演示时可以给一档「压测上限」区间（如 120 / 400 / 800），让「崩不崩」变成
     一条**看得见的曲线**，而不是单点。
   （这一条是演示设计的建议，不是必须做的事 —— 请用户定。）

【1.4 改成「目标 QPS + 持续时长」的方案】

设计口径（推荐）：
  · 新入参 `targetQps`（可选）。给了 ⇒ 启用节拍器；不给 ⇒ **保持现状**（满速）。
  · 节拍器放在**每条线程内部**，速率 = targetQps / plan.size()
    ⇒ 权重仍然保真（线程数就是按权重分的），不用另写按权重放行的逻辑。
  · 用 `LockSupport.parkNanos` + **漂移补偿**（记 t0 与已发条数，睡到
    t0 + k × period），不用 `Thread.sleep` 逐次累加（会漂）。
    参考写法约 20 行。
  · ⚠️ **实际 QPS 可能达不到目标**：`fireOnce` 是**同步阻塞**调用，线程数不够时
    抢不到槽。⇒ **必须在结果里如实报「实际 QPS」**，不能声称打满了。
  · 线程数怎么定：保留 `concurrency` 作为「并发上限」；给了 targetQps 而没给
    concurrency ⇒ 自动 = clamp(ceil(targetQps / 10), 场景数, 500)
    （10 是保守的单线程 QPS 假设，宁可多开线程让它被节拍器压住，
     也不要少开导致打不满 —— 多开是安全方向）。

【2.4 「暂停」的语义（用户已知）】

    正确做法是「停渲染、继续轮询、恢复时用最新值继续」。

四、Q4 核实 · 边高亮节流 + 小字实时计数
=====================================================================

【4.1 ⚠️ 一个必须知道的前提：orders 流的 moves 里没有 batchId】
  `OrderStreamService.drainMoves()`（:108-128）逐字 put 的键是：
    orderId / action / from / to / result / ts
  ⇒ **没有 batchId**。而帧顶层也没有。
  含义：「本批次经过 N 次」**在 orders 流里没有批次号可筛** —— 前端拿到了 moves，
  但分不出「这条是这次演练的」还是「日常流量的」。

  好消息：**修它只要 1 行**。
  `OrderStateEvent` record 里**已经有** `batchId` 字段
  （`MallOrderStateMetrics.java:283-285`，第 11 个分量），
  在 `drainMoves` 的 `row.put(...)` 里加一行：
      row.put("batchId", e.batchId());
  ⇒ 前端就能做「只看本批次的流转计数」。**零 DDL、零新端点。**

【4.2 节流 + 小字计数的口径（用户要的「双管齐下」）】
  · 节流：每秒最多 N 次 flash（N = 3-5）。实现 = 记每个 key 的上次 flash 时刻，
    距上次 < 1000/N 毫秒就跳过。约 10 行。
    ⚠️ **节流只作用于「视觉高亮」，不作用于「计数」** —— 计数走另一条路（见下），
       所以节流**不会丢信息**（这正是用户担心的「显示不过关」的点，答案是：不会）。
  · 小字实时计数：每个节点下方一行小字「本批次经过 N 次」，数字随帧跳动。
    数据源 = moves 里 `batchId === 当前批次 && to === 该节点` 的累计计数。
  · 节点角标（原「每状态多少单」）：保留全表总数（帧里 `counts` 现成），
    **另加**一行小字「本批次 +N」。两行并存，口径各自标清。
