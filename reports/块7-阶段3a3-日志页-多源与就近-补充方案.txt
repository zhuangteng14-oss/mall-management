件一、多源：选**路 1**（三类并入 events 流，加 Kind）
────────────────────────────────────────────────────────────────────────────

【1. 选路 + 理由】
  路 1（并入 events 流，加 3 个 Kind）。顾问倾向也是它，我给出**可复核的四条理由**：
  ① **有现成先例，照抄即可**：审计就是这么进来的 —— Kind.AUDIT（EventBroadcaster.java:137）
     + 源环 AuditMetrics + ingestAudit(:402-418) + fromAudit(:630-636)。新三类走**逐字相同**的路径，
     没有一处是新发明。
  ② **前端合并器零改动**（见第 5 条的修正：路 1 下前端**根本不排序**，少一整个变量）。
  ③ **事件总数可控，有实测数**：7 个 @Scheduled 的周期是 15s / 15s / 60s / 60s / 600s / 3600s
     / 3600s（逐处行号见第 3 条表）⇒ 调度事件**每秒最多 2 条**；慢 SQL 有 200ms 阈值
     （SlowSqlConfig:47）；MQ 有节流（第 4 条给）。对照合并环 2048 槽/拍、本窗实测峰值 143 行/拍
     ⇒ 三类加起来远在余量内。
  ④ **避开 A6**：路 2 要开 3 条新端点，若复用 EventStreamService 就踩「单例 sentSeq(:55) +
     FramePacer(:75) 互串」这条已知实测；各开各的则要复制一整套流服务 —— 代价最大。
  代价（如实，两条）：
    a. 合并环窗口**共享** 2048 槽 ⇒ 三类高频时会挤掉业务事件 ⇒ **必须**给写入口带上限
       （第 4 条的两条节流是硬要求，不是优化）。
    b. ② 的类清单 9 → 12（见件三的高度账），且第 2 条要改一处口径。
  路 2 / 路 3 判否，理由各一条：
    · 路 2 的「断一条不拖累其余」对**同进程内**的三类不成立 —— 慢 SQL 在 DB 拦截器、MQ 在
      publisher/consumer、调度在 @Scheduled，都和审计一样产生在同一个 JVM 里，进程挂了三条一起断。
    · 路 3 的分界线是**假的**：没有任何一条线能把「慢 SQL」划到「内部」而把「MQ / 调度」划到「外部」。

【2. ⚠️ 这条路会改一处口径，要先点头】
  走 路 1 之后，② 里的「**源**」只剩 2 项（事件流 / 演练轮询），而慢 SQL / MQ / 调度变成
  「**类**」不是「源」。⇒ 建议 ② 这样改：
    · 「源」栏保留 2 项（事件流、演练）—— 它回答「这条行是从哪条读法来的」；
    · 类清单**分两组**：业务 9 类（缓存/锁/订单/库存/审计/通知/敏感词/身份/防护）
      + 设施 3 类（慢 SQL / MQ / 调度），两组中间放一条 1px 分隔线。
  ⇒ 好处：新增三类的**筛选路径与既有 9 类一致**（用户不用学两套），且 ⑤ 的链路展开、
  ④ 的类型计数都自动认得它们（都按 kind 分桶）。

【3. 后端改动清单（逐条带文件:行号，可点开核）】
  A 档四项，逐项拆到「改哪一行」：

  A-1 慢 SQL 事件化
    · 新类 `SlowSqlMetrics`（仿既有九环：2048 槽覆盖式环 + recentEvents() 只读快照 + event(...)）
    · `SlowSqlListener.afterQuery`（shared/sql/SlowSqlListener.java:61-69，log.warn 在 :66）
      → 保留 WARN，**再加**一次 metrics 记录。traceId 天然有（回调在请求线程上，类注释 :26 明说）
    · ⚠️ **一处真风险（不是我可以跳过的细节）**：`SlowSqlListener` 是 `new` 出来的
      （SlowSqlConfig.java:77 `new SlowSqlListener(slowMs)`），而装配它的
      `slowSqlDataSourceWrapper` 是 **static @Bean**（:50）—— 它是个 BeanPostProcessor，
      注册时机必须早于普通 bean。若给它加一个 `SlowSqlMetrics` 参数，BPP 就会**提前拉起**
      那条依赖链，Spring 会告警「not eligible for getting processed by all BeanPostProcessors」
      （本类注释 :30-33 正好在讲这件事）。
      ⇒ 处置：慢 SQL 侧**不注入**，改用一个**后置注入点**（listener 持一个 volatile 引用，
        由容器起来后由 metrics 自己塞进去）。落地时按这个走，别图省事加构造参数。
    · 上限（硬要求）：同一条语句模板 N 秒内只记一次 + 每秒条数封顶。理由：afterQuery 对**每条**
      语句回调，压测下每秒数千条慢语句会把 2048 环刷满、把业务事件挤掉。

  A-2 MQ 事件化（**已有链路，只加观测点**）
    · 新类 `MqMetrics`（同上形态）
    · 四个落点（都在现有 fail-soft 路径上，逐字有出处）：
        1. observe/mq/RabbitEventPublisher.java:117-122  发布失败（现在逐条 WARN）
        2. observe/mq/RabbitEventPublisher.java:193-195  MQ 不可达（翻转必记 + 周期 5 分钟）
        3. observe/mq/ObservedEventConsumer.java:129-135 消息非法 JSON ⇒ 单条转 DLQ
        4. observe/mq/ObservedEventConsumer.java:171-173 落库连续 3 次失败 ⇒ **整批**转 DLQ
      ⇒ 3 与 4 就是用户要的「DLQ 事件」，落点现成。
    · traceId：发布侧在 SSE 流线程（MDC 空），但事件对象自带 traceId ⇒ 取 `event.traceId()`；
      消费侧消息体就是 ObservedEvent JSON，同样自带 ✓（⑤ 因此能展开到「是哪条没落库」）
    · ⚠️ **自激/刷屏风险（真风险）**：1 与 3 是**逐条**的。事件化之后，失败会产生事件、事件又要
      发布到 MQ ⇒ 可能自激。现有 `connected` 闸（RabbitEventPublisher.java:102-108「已知连不上
      ⇒ 一次网络都不碰」）把自激限制在「断线后头 5 秒残留窗口」（类注释 :34-36 明说这条残留）。
      ⇒ 处置：**同因节流 60 秒一条**，彻底封住。
    · 顺带收获：`mqDown` 注入于是有了落点（它触发的正是「MQ 不可达」这条已事件化的路径）——
      与既有 TD「INJECTIONS_NOT_WIRED = [mqDown, dbSlow] 没人认领」对齐，本笔可以把它俩一起认领。

  A-3 调度事件化
    · 新类 `SchedulerMetrics`
    · 7 个入口各包一层（grep 实测 7 处 @Scheduled，与用户名单逐个对上）：
        QuestionTimeoutJob.java:96   scanTimedOutQuestions()  delay 600000
        MerchantDowngradeJob.java:65  scanAndApply()          60000
        StatsAggregateJob.java:66     refresh()               60000
        ObservedEventCleanupJob.java:63 prune()               3600000
        OrderTimeoutCancelJob.java:156  advance()             15000
        ShippingTrackAdvanceJob.java:125 advance()            15000
        CouponExpiryJob.java:80       scanExpiringUnclaimed() 3600000
      记什么：job 名 + 结果 + 耗时 + 处理条数。
    · ⚠️ **验收前提（否则判据不可达）**：调度器**总闸**在别人的类上 ——
      `MerchantDowngradeSchedulingConfig.java:22 @EnableScheduling`
      + `:23 @ConditionalOnProperty("mall.downgrade.job.enabled")`；而
      `ObservedEventCleanupService.java:77-78` 逐字写着「**a3 / dev 下调度器总闸是关的**」。
      块 7 用 dev ⇒ **7 个 job 在 dev 下一轮都不跑** ⇒ 调度事件恒空。
      ⇒ 要验它必须**手动放开总闸**（放开后按上面周期等，或临时把某个 delay 调小）。
    · 记法建议：只在**有动作**或**失败**时记（每轮都记会让 ③ 恒有 0.13 条/秒的噪声——
      15s 那两个 job 每轮一条）。这条是我的建议，落地时按你的口径定。

  A-4 EventBroadcaster 加 Kind（三类的公共改动）
    · `Kind` 枚举追加 3 项（EventBroadcaster.java:132-153）——**排在 PROTECTION 之后**，
      依据是它自己写下的规矩 :99-102「不改既有八环的相对顺序」（第九环排最后就是这个理由）
    · `poll()` 追加 3 个 ingest（:264-276）；`sourceSeq` 数组自动跟随 `Kind.values().length`（:231）
      ⇒ **不用改**（这一处容易白改，写明）
    · 构造追加 3 个源环（:233-254）；加 3 个 `ingestXxx()`（仿 :474-495）+ 3 个 `fromXxx()`
      （仿 :668-711，三件套 severity/title/detail）
    · ⚠️ **severity 只许在那一处加**：既有规矩是「severity 规则一处定义」（:52-59、:720-745
      `severityOf`）。新三类的 result 取值（慢 SQL=slow、MQ=publish_failed/unreachable/dlq、
      调度=ok/failed）要**加进 `severityOf` 那张表**，不要在 `fromXxx` 里另写一套。
      档位建议：慢 SQL=warn（与既有 degraded/timeout 同类）、MQ 失败/DLQ=warn、调度失败=error、调度成功=info。
    · ⚠️ **前端必须同步**：`observe-labels.js` 的 `KINDS`（Kind 注释 :129-131 逐字写着
      「加类要两边一起加」）—— 漏了这一处会**静默少 3 类**（不报错，只是筛不出来）。

【4. 两条节流是硬要求（不是优化）】
  · 慢 SQL：同模板 N 秒去重 + 每秒封顶
  · MQ：同因 60 秒一条
  依据同一条：合并环是**共享**的 2048 槽（:122-124），三类高频时会挤掉业务事件，而挤掉是
  **静默的**（只在 droppedIngest 里留个数，:814-841）。开源就必须节流。

【5. 合并排序怎么答（修正我上一轮的说法）】
  上一轮我写的「三键排序 (ts, sourceRank, 游标)」是**在「各源独立流」的假设下**写的；
  走路 1 之后**作废**，而且**不应该**按 ts 全局排 —— 理由是后端自己给出的（硬理由，别绕过）：
  `EventBroadcaster` 类注释 :92-102 明写「同一拍内的顺序 = **环序**，不是事件发生的先后」，
  且给出原因：**各环的墙钟只保证「同环内单调」** ⇒ 跨环的 ts **不构成全序**，按 ts 全局排序
  会得到**不稳定、不可复现**的顺序（同一批数据两次排不一样）。
  ⇒ 路 1 下的正确口径：
    · 主源（事件流）：**按帧接收顺序 append，零排序**（后端已定序，前端不重排）
    · 第二源（演练轮询）：**只与自己的历史比，按到达时刻插在尾部**，不回溯插入、不与事件流交叉排
    · 迟到丢弃：仍然要（帧里带 dropped，③ 上屏「迟到丢弃 k 条」）
  好处：前端合并器只剩「append + 计数」，没有排序器 —— 这是选 路 1 的第 ② 条理由落到实处。

【6. 顺带发现的一个真问题（要你裁，见件四）】

先复述约束：**不合并**（两块各自独立），但**物理位置靠近**（联动时视觉路径短）。

【1. 三个方案的判】
  方案 A（错误率挪到 ④）—— **否决**。① 是「全局一眼」的读数带，错误率是它最该有的读数
    （你自己也这么说了）；挪走之后 ① 缺一块「现在坏不坏」。
  方案 B（严重度分布做成 mini 三色条进 ①）—— **选它**。① 排 1 里：错误率数字 + 紧挨着的
    mini 三色条（比例）。宽账：现有六个读数 ≈840 + 三色条 ≈90 = ≈930 ≤ 可用 1144 ✓ 装得下。
  方案 C（垂直相邻）—— **甲版不成立**（① 满宽、④ 在右栏，被一整栏隔开 —— 你自己点出的代价）；
    但**丙版天然成立**（④ 是横带、与 ① 垂直贴合）。
  ⇒ 结论：**两版统一走 B**（① 是共用件，不在这里分叉）；丙版**额外白得 C**。

【2. 两块怎么分工（不重复画同一件事）】
  · ① 的 mini 三色条 = **比例 + 交互入口**（点它 = 过滤，见第 3 条）
  · ④ 的严重度分布 = **数目 + 占比**（与 Top N 榜同框，回答「错的是哪些类」）

    就是它的构成，不用移视线。

【3. 联动具体是什么（两个方向，各一条）】
  L1 · 人 → 数据：点 ① 三色条某一档 ⇒ ② 的严重度三档**同步勾选** + ③ 立即过滤。
      再点一次取消（三色条 = 严重度快捷开关）。
  L2 · 数据 → 人：错误率 **> 0** ⇒ 三色条 error 段脉冲 **2 次**（不循环）+ ① 的错误率数值变红。

      ⇒ 任何「比如 > 5%」的阈值在本窗**永远不触发**，会变成一条不可达的判据。
  L3（可选）· 悬停某档 ⇒ ③ 里该档的行**短暂高亮**（不改过滤，只看一眼），移开恢复。

【4. ⚠️ 降级的拦路石：这三条在真数据上全部看不见】
