当前长列表接口盘点报告
================================================================
日期      ：2026-10-17
分支      ：feat/c3-admin-block7（块 7 收尾 · 合并前加固）
范围      ：Mall-management-server 全部 Controller + 对应 DAO/SQL + Mall-management-web 调用面
方法      ：静态代码盘点（只读）。每条结论都可复核到「文件:行号」；
            本报告**未**对每个端点做运行时压测，量级判断是「随业务增长」的结构性推断。
            唯一有运行时数据的是 /goods/goodsSelectHome 一族（块 7 压测走的缓存价格路径，不是列表路径）。
证据等级  ：【可复核】= 源码逐行读到；【推断】= 由表结构和调用面推出，未实测。

一、结论摘要
----------------------------------------------------------------
1. 真正同时具备 limit + offset、且 SQL 落到 LIMIT ? OFFSET ? 的 DB 列表端点
   共 10 个（清单见第二节）。
2. 大多数列表端点只有 limit（SQL 只有 LIMIT ?，没有 OFFSET），属于
   「截断式上限保护」，不是真正翻页 —— 超出上限的数据不可达。
3. 没有任何 DB 列表端点出现「传了 limit 但 SQL 完全不用」。
   唯一例外是 /admin/observe/metrics/history：limit 作用在内存滚动窗口（最多 60 条），
   不是 SQL LIMIT，属于设计如此。
4. 风险最高的无分页端点集中在：消息（history / conversations）、订单（用户端与商家端
   四条）、营销券包（myCoupons）、统计商家榜（admin/stats.merchants）。
5. 后端不存在「接收 offset 但不绑定」的端点。
6. 轮播图、公告、死信、库存均没有独立的后端列表端点（见第七节）。

四、完全无 LIMIT（风险最高，随业务线性增长）
----------------------------------------------------------------
【可复核】

  - POST /message/history
      双方全部历史消息，ORDER BY create_time ASC，无 LIMIT
      MessageDao.java:148-151；Controller MessageController.java:84-89
      前端 ChatRoom.vue:257 初次全量加载、:315 轮询追加。
  - POST /message/conversations
      按参与账号扫 message 表 + GROUP BY，无 LIMIT
      MessageDao.java:111-119；Service 逐会话 N+1 查已读时间（MessageService.java:144-181）
  - POST /order/orderSelect
      按 CustomerId，无 LIMIT；OrderDao.java:195-197
  - POST /order/orderDeliveryIfSelect
      按 MerchantId，无 LIMIT；OrderDao.java:202-204
  - POST /order/orderDeliverySelect
      按 MerchantId + status，无 LIMIT；OrderDao.java:215-222
  - POST /order/historicalOrdersSelect
      按 CustomerId + 已收货，无 LIMIT；OrderDao.java:228-232
  - POST /marketing/myCoupons
      按账户取券包全量，无 LIMIT；CouponDao.java:447-470
      前端 CouponWalletDialog.vue:213 注释明确「myCoupons 不分页（后端给全量）」
  - POST /admin/stats 的 merchants 列表
      GROUP BY MerchantId，无 LIMIT；StatsDao.java:108-118
      前端商家榜全量渲染。
  - POST /goods/goodsSelect
      不是无 LIMIT，而是**硬 LIMIT 200**（GoodsCacheService.java:227-229），无 offset；
      MerchantId 无索引、注释明确全表扫（:215-219）。
      前端 GoodsUp.vue:190-200 的 Pager 只是对这最多 200 行做**前端分页**；
      >200 件商品会被后端静默截断（:675-690）。

六、本次「块 7 收尾」已落地的分页口径
----------------------------------------------------------------
【可复核】只动商城端与三个管理端列表，未做全仓翻页改造：

  1. /goods/goodsSelectHome、/goods/productSearch、/goods/categoryGoods

  以及所有「仅 limit」的运营列表 —— 改动面大会牵动前端分页器与契约，未在本次加固中擅自铺开。

七、没有独立列表端点的域
----------------------------------------------------------------
【可复核】
  - 轮播图：无独立 Controller/表端点；首页取 /goods/goodsSelectHome 第一页前 5 条
    （HomePage.vue:348-356）。
  - 公告：无独立公告列表；发送 /admin/notify/send，历史 /admin/notify/history，
    接收面 /notification/list。
  - 死信：无列表端点；只有 DLQ 常量 observed_event.dlq
    （RabbitObserveConfig.java:93）、消费者重试耗尽转 DLQ
    （ObservedEventConsumer.java:186-212）与累计计数指标 mall.observe.dead.letters
    （:111）；指标帧以 dlq:{total,delta} 暴露（MetricsSnapshotService.java:363-370）。
  - 库存：无独立 HTTP 列表端点；/goods/skuList 是单商品 SKU 矩阵，
    指标快照内部另有 goods_sku 库存水位（最多 20 条，MetricsSnapshotService.java:142,449）。
  - 店铺关注：只有 follow/unfollow/state，没有关注列表端点。

八、结论与建议（本次未实施）
----------------------------------------------------------------
1. 合并前判据已满足：商城端列表不再全量返回，管理端用户/演练记录具备真翻页，
   订单与审计有上限兜底。风险点已如实登记，不在收尾笔里夹带跨域重构。
2. 若后续要收口，建议顺序：
   a) /message/history + /message/conversations（增长最快、无上限）；
   b) 用户/商家四条订单列表（加 limit + offset，前端接 Pager）；
   c) /admin/audit/list、/admin/order/list、/notification/list 补 offset；
   d) /goods/goodsSelect 改真分页（顺带解决 MerchantId 全表扫）；
   e) /marketing/myCoupons 与 /admin/stats.merchants 评估是否设上限。
3. 上述每一项都会改动前后端契约，应按附录 J.2 的口径逐笔登记，不要一次性铺开。
