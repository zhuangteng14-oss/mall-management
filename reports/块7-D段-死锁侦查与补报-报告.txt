【一】死锁侦查实测（顾问追加 · 任务 1 / 任务 2）
───────────────────────────────────────────────────────────────────────────

■ 1.0 结论一句话 ─────────────────────────────────────────────────────────

真死了。用**产品自己的两个真实端点**并发压，48 轮 ×(1×A + 4×B) = **48/48 轮全中**，
共 **149 次** ER_LOCK_DEADLOCK。
没有用裸 SQL 造环；没有先落重试再补实验；没有在 a3 下做。


■ 1.1 哪两个端点、为什么是这两个（不是拍脑袋挑的）──────────────────────

A（慢起手）= POST /admin/accounts/application/audit   参数 id=<申请Id>&approve=true
     → MerchantApplicationService.audit（@Transactional）→ promote(...)
     写序：merchant_application → **user** → login → merchantimage → **user** → **goods**
     （最后那条 goods 只在「DowngradeState='frozen' 且 FreezeUntil 未过」时才走到）

B（快起手）= POST /admin/accounts/downgrade/relist     参数 username=<同一账号>
     → MerchantDowngradeService.relist（@Transactional）
     写序：**goods** → **user**

⇒ {user, goods} 两张表 **反向**。这条环要成立，只需要「两个事务同时持着对方要的那把」。


■ 1.2 为什么全仓只有这一对（顾问给的候选范围我走完了）──────────────────

| 候选 | 实测写序 | 能不能成环 |
| GoodsService.goodsAdd | 只写 `goods_audit` 一张表 | 单表，不可能 |
| GoodsService.goodsDe  | goods → productsales（同序） | 无反向对，不能 |
| GoodsService.goodsUp  | goods → productsales（同序） | 无反向对，不能 |
| OrderService.orderAdd | 同序 | 不能 |
| MerchantDowngradeService.applyFreeze | login → goods → user | **不能**（见下）|

· 全仓**没有**第二条 productsales → goods 的路径 ⇒ GoodsService 无反向对。
· `applyFreeze`（定时到期的自动降级）**不是 @Transactional** —— 类注释明写
  「逐条自动提交 + 末位翻状态」。每条语句各自一个事务 ⇒ 持锁不跨语句 ⇒
  **结构性构不成环**（这一点我专门找了，怕漏掉「不需要人操作就能撞上」的路径）。
· `cancel` / `schedule` 同样是单语句，同理。

⇒ 全仓唯一反向锁序对 = `audit`(user→goods) × `relist`(goods→user)。


■ 1.3 压了多少次 / 重现率 ───────────────────────────────────────────────

| 规模 | 轮数 | 每轮并发 | 出死锁的轮数 | 1213 增量 | relist 侧失败 |
| 48 × KB=4 | 48 | 1×A + 4×B | **48/48 = 100%** | **149** | 149/192 = 77.6% |
| 36 × KB=1（第一遍） | 36 | 1×A + 1×B | 10/36 = 27.8% | 10 | 10/36 |
| 36 × KB=1（第二遍） | 36 | 1×A + 1×B |  4/36 = 11.1% |  4 |  4/36 |
| KB=1 两遍合计 | 72 | | 14/72 = 19.4% | 14 | |

⚠️ **单点数字不可复现，按分布给**：KB=1 两遍跑出 10/36 与 4/36（差 2.5 倍）。
   第一遍 36/36 轮 A 都走到了 goods 那一腿；第二遍只有 31/36 走到
   —— 那 5 轮是 B 先跑完赢了（A 读到 DowngradeState 已是 'none'），
   **天然不可能成环**。所以「KB=1 的重现率」本身带一个上界。

· 错开量 0 / 1 / 2 / 3 / 4 / 5 / 6 / 7 / 8 ms **每一档都中**（KB=4 下每档 4/4 或 8/8）
  ⇒ 不是「只有某个精确时序才中」。
· `ER_LOCK_WAIT_TIMEOUT` 全程 **0** ⇒ 是**真死锁**（被立刻判出），不是锁等待超时。
· 失败**全在 relist 一侧**：A 侧 48/48 全部 `outcome=approved-restored`、0 次 5xx。
  KB=4 的 149 次失败里，B 占 149、A 占 0。

■ 1.5 为什么窗口这么宽（是机制，不是运气）──────────────────────────────

`goods` 表（`mall_management_sql.sql:54`）**只有 PRIMARY KEY (`Id`)**，没有 MerchantId 索引；
`user` 表（`:182`）只有 PRIMARY KEY (username)，没有 merchantid 索引。
REPEATABLE-READ 下 `UPDATE ... WHERE MerchantId = ?` 会**扫描全表并把扫到的每一行都加 X 锁**。
INNODB STATUS 里 T2 持有 **49 行**（`goods` 表约 45 行 + supremum）就是这条的直接证据。
⇒ 这条环的成立不依赖毫秒级巧合，靠的是「一条不命中索引的 UPDATE 锁住了整张表、
   并且一直持有到事务结束」。

■ 1.7 最小复现步骤 ───────────────────────────────────────────────────────

    node scripts/probes/d2-deadlock-scout.mjs --cleanup            # 只清夹具
    # 退出码 0 = 至少死了一次；1 = 一轮都没死

夹具等价于走完「降级排定 → 到期执行 → 商家重新申请」三步，探针用 SQL 直接置成那个态：
    user:                DowngradeState='frozen', FreezeUntil=NOW()+10d
    merchant_application: Status='pending'（同一账号）
    goods:               该商家名下一行，ShelfState=0
每轮复位后，同一瞬间发 A×1 + B×K。

**阳性对照**（证明「判据是活的」，不是业务结论）：
    bash scripts/probes/d2-deadlock-control.sh
两个会话在 `goodstype` 上反序 `SELECT ... FOR UPDATE`（**只读锁 + ROLLBACK，不写任何一列**），
跑出 `ERROR 1213 (40001)` + 计数器 0→1 + INNODB STATUS 出现死锁段。
⚠️ 这个脚本**不是**顾问禁止的「为了能让重试做而人为构造假死锁」——
它一次数据都不写，只用来排除「本实验的 0 会不会其实是检测链坏了」这一类失败模式。


■ 1.8 诚实性声明（别让上面读起来比实际更强）────────────────────────────

1. **两条并发动作都是真实端点、真实业务逻辑**；没有用裸 SQL 造环。
2. 但**夹具状态是 SQL 直接置的**（等价于走完三步业务，但那三步本身没在这次实验里跑）。

5. 「全仓唯一反向锁序对」是**静态读源码**得出的，不是穷举证明
   —— 我穷举的范围是「带 @Transactional 的多表写路径」（真实注解 13 处）。
6. A 从不失败、B 必失败这个**不对称**是实测到的（149:0），我没有进一步深挖
   InnoDB 的受害者选择判据；这不影响结论（无论谁是受害者，都是一条合法管理请求拿到 500、活儿白丢）。
