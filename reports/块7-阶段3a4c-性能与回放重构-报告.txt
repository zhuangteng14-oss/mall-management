────────────────────────────────────────────────────────────────────────
一、这次要求的判据（原话口径）
────────────────────────────────────────────────────────────────────────
① 不卡顿：CDP 打开指标页，录 3 秒 Performance Trace；切到日志页再切回指标页。
   切页期间不允许出现 >100ms 的 Long Task；日志列表 DOM 渲染必须 ≤200 条。
② 回放逐帧：每 500ms 采样一次，连续 4 次；屏上事件行数必须一点点变长，
   不能第一秒就把几千条全塞进去。
③ 不允许用「接口通了 / 最后有数据」糊弄，必须测「过程」。

────────────────────────────────────────────────────────────────────────
二、实测到的根因（不是靠猜）
────────────────────────────────────────────────────────────────────────
1. 日志列表本来就有虚拟滚动，内存 2,048 条时只渲染 ~20 行；
   但**首帧窗口上限写的是 200 行**（vEnd = VIRTUAL_MIN + OVERSCAN×2）：
   第一次进日志页会先铺 200 行复杂 DOM，仅 Layout 一项就实测 >100ms。
2. 指标页 5 个 BaseChart 在同一帧里做 init / resize+setOption：
   切回指标页时 5 次重绘合并成一个 **225ms** 的 Long Task。
3. 日志页是懒加载路由：第一次切过去要现场执行它的 chunk，
   EvaluateScript 一项约 **46ms**，也是那个 130ms Long Task 的组成部分。
4. KeepAlive 驻留期间，隐藏页的 computed / 滚动 / 补间 / 图表仍可能被驱动。
5. 回放把整批事件一次交给 Vue（list.concat(all) 式的做法），没有按原始时间差推进。

────────────────────────────────────────────────────────────────────────
三、改动（文件 + 做了什么）
────────────────────────────────────────────────────────────────────────
EventLog.vue
  · KeepAlive 门控：onDeactivated 停掉 streamRows 的 watch、滚底、每秒时钟；
    SSE 仍照收（数据不丢），onActivated 用最新数据补一帧。
  · 渲染硬上限：updateWindow 里 vEnd 夹到 s + VIRTUAL_MIN（200）。
  · 首帧只铺 40 行（vEnd 初值 200 → 40），再按视口＋overscan 收窄。
  · 内存仍保留 2,048 条，「全部」缺省与 DOM 上限彻底解耦。

BaseChart.vue
  · onDeactivated 后绝不 setOption / resize；激活时用最新 option 补一帧。
  · 新增模块级队列：五张图的 init / 激活重绘一帧只做一张（单帧回到几十毫秒）。

MetricsPanel.vue
  · onDeactivated 取消 rAF 与 KPI/库存数值补间；SSE 数据照收；
    onActivated 按最新一行补上数值。

AdminShell.vue
  · 首屏后 requestIdleCallback 预取日志页 chunk（只求值、不渲染，路由仍懒加载），
    把首航日志页约 46ms 的 EvaluateScript 摊到空闲帧。

AttackConsole.vue（回放引擎重写）
  · 全量台账只放非响应式 replayData，模板只读 replay.played（≤400 条）。
  · 每条按「原始 OccurredAt 相对首条的偏移」乘统一 scale 得到播放时刻；
    密集批次按每帧 3 条能放完的最短时长拉长（封顶 60s），稀疏批次等速。
  · requestAnimationFrame 每帧最多吐 3 条；屏上最多留 400 条只影响画面，
    cursor 仍按全量推进。没有 list.concat(all)，也没有几千个 setTimeout。

────────────────────────────────────────────────────────────────────────
六、需要说清的口径 / 局限
────────────────────────────────────────────────────────────────────────
1. 本报告数据来自 headless Edge（--headless=new），不是人工肉眼观察；
   FPS 58 是该环境下的平均值，headed 模式会因窗口合成略有差异。
2. Long Task 判据用的是浏览器 PerformanceObserver 的 longtask 条目
   （>50ms 全部列出，>100ms 必须为 0），这是「切页期间」的严格口径；
   CDP Trace 作为过程对照，本版 Edge 不产出 RunTask，故未用 RunTask 计数。
3. 日志页是懒加载路由：首次进入的 chunk 求值被 AdminShell 在空闲帧预取掉了。
   这是真实的性能处理（真实用户也受益），不是只在探针里跳过的作弊；
   路由仍然是懒加载，只是提前求值模块。
4. 回放的 400 条是**屏上保留上限**，不是载入上限：cursor 仍按 3,892 条全量推进。
5. 回放截图只截了可视区域，列表内部滚动到底部，所以每张图看起来行数相近；
   「一点点变长」的判据以同一时刻采样的行数 / cursor / DOM 节点三列为准
   （123 → 228 → 311 → 400，节点 1,568 → 3,507）。
