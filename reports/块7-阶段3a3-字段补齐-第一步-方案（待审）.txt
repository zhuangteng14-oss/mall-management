§零  先说三件「和你原话不一样」的事 —— 都会改变工作量
════════════════════════════════════════════════════════════════════

【0.1】你说「耗时」主要加在 metrics 类里 —— **做不到**。实测：9 个 metrics 类里
       只有 **3 个**有现成计时（cache.probe / lock.acquire / order.asyncDuration），
       其余 **6 个类一个字都没测过**（StockMetrics / AuditMetrics / NotifyMetrics /
       SensitiveMetrics / IdentityMetrics / ProtectionMetrics 全无 Timer、无 nanoTime）。
       而「库存扣减从哪到哪」「状态流转 CAS 前到 CAS 后」这类起止点**根本不在 metrics 类里**
       —— metrics 类只在业务调用点被「通知一声」，它看不见起止。
       ⇒ **必须改业务调用点**（OrderService / AuditService / NotificationService /
       SensitiveWordService / IdentityGuard / InboundRateLimitInterceptor /
       OrderTimeoutCancelJob / MerchantDangerService 等），并给这些 public 方法**加入参**。
       这就是「半天 → 1–2 天」的真实来源，不是估计。

【0.2】你说的 `durationMs` —— 对**缓存 L1 会恒为 0**。L1 是 Caffeine 本地缓存，
       `getIfPresent` 是纳秒级（命中约 0.2–1 µs），整数 ms 永远是 0。
       建议改 **`durationUs`（微秒）**，前端按阈值显示（<1000 µs 显 µs、否则显 ms）。
       ⇒ 这是对你原话的**偏离**，要你点头（§八 待裁 ①）。

【0.3】审计环**已经有** `actor` 字段了。`AuditEvent` 的分量里本来就有
       `String actor`（javadoc 逐字：「谁写的（业务号，会话取值）」）。
       ⇒ 审计环的「谁」**不用新增**，只需补 `actorRole`；`actorId` 直接复用现有 `actor`。
       其余 8 环的 record 里都没有任何「谁」。

§三  detail 结构化草案
════════════════════════════════════════════════════════════════════

口径（四条）：
  1. **`detail` 一个字符都不改**（后端 `EventBroadcaster.fromXxx()` 的原样拼接保留）
     ⇒ 老前端、老测试、已入库的 60 拍真帧全部不受影响。
  2. **新增 `fields`**，类型 `Map<String,Object>`（混合类型：`qty` 是数字、`result` 是字符串）
     ⇒ 序列化成 JSON 后就是原生类型，正合你给的例子。
  3. **fields 从源 record 的分量抽，不解析 detail 字符串**
     ⇒ 不做正则往返（那会在 detail 改文案时悄悄失配）。
  4. **fields 要自足**：前端「优先读 fields」要求只读 fields 就能拼出完整句子
     ⇒ 顶层已有的 `key` 也在 fields 里重复一份（顶层那份是给过滤/排行榜用的）。
