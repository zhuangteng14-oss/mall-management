E · 【重点】跨线程透传端到端（8c 判据① —— 本笔补齐的那条）
================================================================================
背景一句话：请求线程上的 `(traceId, batchId)` **搬**到演练自己的 `drill-*` 线程上
（ObserveContext），再作为出站头 `X-Drill-Batch` 带进服务端（TraceIdFilter 写 MDC），
于是演练打出来的事件才带得上批次号。8c 当时只验到「单元 + 日志」，**端到端没跑**——
本笔补上了，下面是判据与实测。

步骤 E-1  **先**打开「实时日志」页（或等价地先挂一条流）：
          curl.exe -N -m 60 -X POST http://localhost:8088/admin/observe/events/stream
          判据：〔当场看〕终端开始一行行出 `data: {...}` 帧

步骤 E-2  跑一轮（并发 4、持续 8~10 秒、勾 3 个场景）：
          curl.exe -X POST http://localhost:8088/admin/observe/attack/run \
            --data-urlencode "name=手验-跨线程" --data-urlencode "concurrency=4" \
            --data-urlencode "durationSeconds=8" \
            --data-urlencode 'scenarios=[{"key":"orderBurst","weight":50},{"key":"seckill","weight":30},{"key":"sensitiveWord","weight":20}]'
          期望：HTTP 200，body 里有 `Id` / `TotalRequests` / `BlockedRequests`
          判据：〔可复核〕HTTP 200 且 TotalRequests > 0

步骤 E-3  取这一轮的批次号
          判据：〔可复核〕SELECT Id, BatchId FROM drill_record ORDER BY Id DESC LIMIT 1;
                ⇒ 记下这个 BatchId（形如 102973f7-b9ac-4f52-8940-bb9d27c30018）

步骤 E-4  **判据① 核心**：查这个批次的台账
          判据：〔可复核〕
                SELECT COUNT(*) AS Rows_, COUNT(DISTINCT BatchId) AS Batches,
                       COUNT(DISTINCT TraceId) AS Traces, COUNT(DISTINCT Kind) AS Kinds,
                       MIN(OccurredAt) AS T0, MAX(OccurredAt) AS T1
                  FROM observed_event WHERE BatchId = '<E-3 的批次号>';
            a) Rows_ > 0                       —— 事件确实落了库（不是空批次）
            b) Batches = 1                     —— 一个不漏，也没混进别的批次
            c) Traces > 1                      —— 每条子请求各自一个链路号 ⇒「批次 ≠ 链路」，
                                                  这正是批次号存在的理由（traceId 串不起一整轮）
            d) Kinds ≥ 2                       —— 至少两类事件带上了同一个批次
            e) MIN/MAX(OccurredAt) 落在 E-2 那 8 秒（±2 秒）内
          〔本笔已实测〕3697 行 / 1 批次 / 1194 trace / 5 类 / 23:08:33–23:08:41
                        证据 docs/agent/evidence/c3-block7/b7c9-e2e-batch.txt

步骤 E-5  **反证 1（别把正常值当故障）**：查 `BatchId IS NULL` 的行
          判据：〔可复核〕
                SELECT Kind, COUNT(*), MIN(OccurredAt), MAX(OccurredAt)
                  FROM observed_event WHERE BatchId IS NULL GROUP BY Kind;
                ⇒ 会有行（本笔实测 420 行，全是 stock 类，时间落在两次演练之间）
                ⇒ 它们是**非请求上下文**（定时任务等）产生的事件，`NULL` 是**正常值**
                  （8b 建表时列注释就这么定的）——判据是「该批次的行数对得上」，
                  **不是**「全表都带批次」。看到 NULL 就报「透传漏了」是误判。

步骤 E-6  **反证 2（已知边界，别误判成故障）**：不开任何流，再跑一轮，当场查 E-4
          判据：〔可复核〕当场查 = 0 行；**然后**打开实时日志页再查同一批次 ⇒ 行出现了，
                且 `OccurredAt` 仍然落在演练当时那几秒（不是「现在」）
                ⇒ 「0 行」的成因是**落库滞后到有人读流**，不是透传丢了
          〔本笔已实测〕第一轮不开流：当场 0 行 → 开流后同一批次 2140 行，
                        时间戳 23:06:51–59（演练当时）；证据同 §E-4 那个文件

步骤 E-7  页面侧对一眼
          判据：〔当场看〕实时日志页里那一轮的事件，抽屉按 traceId 能聚成「这一次请求的链路」；
                卡片上的批次/链路字段与 E-4 的数对得上

判据 H-1  〔可复核〕SELECT COUNT(*) FROM observed_event WHERE BatchId='<E-3>'; 数对得上
判据 H-2  〔可复核〕drill_record 里留了本笔两次收口验证的行（Name = `b7c9-e2e` / `b7c9-e2e2`）——
