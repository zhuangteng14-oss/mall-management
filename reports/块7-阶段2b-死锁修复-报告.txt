  治因（丙）加索引
    · Migration ⑳：`goods` 上的 `idx_goods_merchant (MerchantId)`
    · 只加索引：不改列、不删行、幂等（`information_schema.STATISTICS` 守卫 + PREPARE/EXECUTE，
      照本文件 ⑭ 先例；走「文件末追加的迁移块」⇒ 其后行号零移动）
    · 落在：mall_management_sql.sql 段⑳ · docs/agent/db-schema.md §18 · db-migration.md 注意 24
    · ⚠️ `user.merchantid` 的同类索引**本次不加**：裁定原文「留 agent 实测后再定」，
      实测的答案就是「不必」——`user` 侧那条 `UPDATE user … WHERE username = ?` 走的是 PRIMARY
      （`user` 的主键就是 `username`），本来就只锁 1 行；那 49 行锁全部来自 `goods` 侧。
      （2026-10-16 顾问追问后补实测复核：`EXPLAIN UPDATE user … WHERE username = ?` ⇒
       `key=PRIMARY` / `key_len=80` / `rows=1` / `filtered=100`（MySQL 8.4.11）；
       且三份 INNODB STATUS 死锁段里，**user 侧被持有的锁恒为 1 条 record lock**
       （`index PRIMARY of table user … lock_mode X locks rec but not gap`），
       `49 row lock(s)` 只出现在基线那一份、且全部在 `goods` 侧。⇒ 结论成立，不加。
       原始输出：docs/agent/evidence/c3-block7/d2-user-explain.txt）

  ⚠️ 索引不治本环 —— 环的成因是两个事务访问顺序相反，与各自锁住几行无关。索引只把锁粒度
     从「持 49 row lock」压到「单条 record lock」，缩小牵连面，不拆环。真正兜住 500 的是
     重试（见对照表第三行：5xx = 0）。

     （这一段是**裁定要求写进三处**的其中一处（本段与迁移块注释为**逐字**，TD-76 按要点重述）；
       另两处 = `docs/agent/tech-debt.md` 的 TD-76、`mall_management_sql.sql` Migration ⑳ 的
       块注释。理由：防后人看到「死锁问题 + 有索引」以为索引治好了，把重试删掉 ⇒ 500 立刻回来。）

  治果（甲）落重试

    · 形态：装配**编程式** RetryTemplate（要读运行时开关，故不用注解 @Retryable）
      次数 3（RELIST_MAX_ATTEMPTS）/ 退避 40ms 起 ×2 封顶 200ms / 只认 CannotAcquireLockException
    · ⚠️ 重试在事务之外：relist 不挂 @Transactional，事务由内层 TransactionTemplate 开
      ⇒ 每次尝试都是一个新事务（两条结构钉钉住）

三、被实测推翻的两条预判（TD-74 订正）
================================================================================

  1. 落点：原判 = GoodsService 三处写方法 ⇒ 实测 = MerchantDowngradeService.relist
     全仓**唯一**的反向锁序对是 audit(user→goods) × relist(goods→user)；
     GoodsService 那三处不在任何一个环上。
     ⇒ 「多表事务 ⇒ 死锁只可能在这类地方」这条推理链没错，
       错的是「本仓的多表事务里恰好有反向对的那一对在哪」。

  2. 锁侧：原判「两表都只有主键、两条 UPDATE 都全表扫描」⇒ 实测只有 goods 侧全表扫。

五、其他实现要点（都是实测）
================================================================================

  · RetryTemplate 是「先问 canRetry、再执行」的循环
    ⇒ 把运行时开关直接短路在 canRetry 上，会让「关掉重试」变成「连第一次都不执行」
      （抛 RetryException，且它**没有 cause** —— 原始死锁在异常链上就丢了）。
      修法一行：if (context.getLastThrowable() == null) return true;
    另：RetryContext.getRetryCount() 首次为 0 ⇒ attempt = count + 1。

  · 重试发事件时也带 traceId / batchId（记录那一刻从 MDC 取，与既有九环同款）。

  · 结构钉两条（RelistDeadlockRetryTest）：
      ① 反射断言 relist 上没有 @Transactional
         （有人加回去 ⇒ 重试退化成「在已回滚的事务里重试」）
      ② 计数替身 CountingTxManager 断言每次尝试各起一个新事务
