二、用户需求与落点
────────────────────────────────────────────────────────────────────
【一、前端接收与 DOM 渲染解耦】全部落地在
  Mall-management-web/mall-management-system/src/views/admin/observe/EventLog.vue
  · SSE 收帧只 push 非响应式 rawBuf（normal / demo 两桶），不直接改 Vue 的 events。
  · setInterval(100ms) 批量冲刷 flushBuffer()：800 次/秒的更新合并成约 10 次/秒。
  · UI 反压：events 最多保留最近 200 条（EVENT_CAP=200），超出在内存丢弃。
  · 冻结：点「暂停」或手动上滚（autoBottom=false）时不冲刷，数据只进 rawBuf；
    rawBuf 自身有 4096 上限，超出丢最旧；恢复（继续 / 滚回底部）后一次性吸收。
  · rawBuf 与 events 分离后，冻结期间原始数据不丢，只是不渲染。

【二、后端按秒聚合限流事件】
  Mall-management-server/.../protect/InboundRateLimitInterceptor.java
  · 拦截时不再逐请求发事件，改为 AtomicLong 累加；
  · 单线程 daemon 调度器每秒收口一次，只发一条汇总事件：
    「入站限流触发：该秒内拦下 N 次请求（示例 method=... path=...，limitForPeriod=...）」。
  · ProtectionMetrics 仍是双通道：请求计数按次累加（指标口径不变），事件环每秒只写一条。
  · ProtectConfig 负责启动聚合器；@PreDestroy 关闭。

  探针 scripts/probes/c3b7-3a4d-backpressure.mjs，产物

    并在演练中验证「暂停」「上滚」冻结与恢复。

【第二步：动态背压 + 智能聚合】
  · MAX_RENDER_PER_TICK = 200（实测写死，见下节数据）：一拍内 batch ≤ 200 原样逐条；
    超过 200 才触发聚合。
  · 聚合键 = kind + title；同组 ≥2 条合并为一条，保留最新一条的上下文，附 aggCount 与 seqs；
    单条低频原样保留。
  · UI：聚合行右侧 ×N Chip；点行在 ⑤ 抽屉提示「已折叠 N 条同类高频事件」。
  · 注意：MAX_RENDER_PER_TICK 只决定「是否触发聚合」，不直接截断；真正的 UI 上限是 EVENT_CAP=200。

四、本轮修掉的一个真实 Long Task（不是探针噪声）
────────────────────────────────────────────────────────────────────
首轮演练出现 1 次 66–68ms Long Task。用 _work/3a4d/diag-lt.mjs 每 200ms 对齐页面状态后定位：
  streamRows 在 200~204 行之间抖动（EVENT_CAP 200 + trace 的请求起止脚手架行进出），
  virtualOn 用「>200」单阈值判断 ⇒ 掉到恰好 200 行时退出虚拟滚动，一次性挂载 200 行真实字段。
修复：窗口化开关加滞回。
  · 超过 200 行才进入虚拟滚动；
  · 降到 160 行以下才退出（VIRTUAL_OFF_BELOW = VIRTUAL_MIN − 100）。
回归（Phase A2，最终一轮）：
  201 行 → virtual=true，DOM 23；
  200 行 → 仍 virtual=true，DOM 23（无滞回时这里会挂 200 行）；
  99 行  → virtual=false，DOM 99；
  整个过程 >50ms Long Task = 0。
说明：滞回只影响「何时用窗口化渲染」，数据侧仍保留 events 最近 200 条，语义不变。

六、智能聚合单元（Phase B）
────────────────────────────────────────────────────────────────────
一次注入 500 条「缓存命中」+ 1 条「锁等待超时」：
  聚合前 501 条 → 聚合后 2 行；
  1 条聚合行 ×500（aggCount=500），1 条单条行「锁等待超时」；
  DOM 2 行，Chip 文本「× 500」。
⇒ 高频同类被合并，低频业务不被误伤。
